# BIN-SYNC CORE v3.0.0 — нормативная спецификация
## Универсальный протокол синхронизации и контракт долговременного состояния

**Статус:** v3.0.0 DRAFT — целевой обязательный контракт для реализации и conformance.
**Дата редакции:** 2026-11-08.
**Тип изменения:** breaking / clean cut. Форматы v2.x не поддерживаются.

> Нормативный приоритет: эта редакция v3.0.0 — единственный источник требований BIN-SYNC. Текст после заголовка «Историческая справка v2.4.22» оставлен только для трассировки дизайна. Он не задаёт wire/storage compatibility и не разрешает fallback. При расхождении действует v3.0.0.

## 0. Краткое содержание обязательных изменений v3

1. Каждая опубликованная операция несёт неизменяемую Origin provenance: (originAuthorNodeId, originAuthorEpoch, originSequence). Она создаётся исходным автором при freeze и сохраняется без изменений через WAL recovery, receive, PendingApply, storage, relay и повторную доставку. Текущая-state snapshot image не является набором PublishedOperation: она несёт собственную signed snapshot-generation provenance и сохраняет исходные field-author/HLC значения; ей запрещено синтезировать ChangeId/OriginSequence для исторических операций.
2. ChangeId остаётся глобальной route-independent identity: (scope, namespaceId, ChangeId). Origin — provenance, а не замена ChangeId. Один ChangeId с отличающимся semantic fingerprint или Origin — equivocation и отклоняется до мутации.
3. Одна логическая операция и один immutable payload обслуживают любое число получателей. Отдельно хранится компактный прогресс по (peer, namespace, author stream); per-peer копии payload и ACK bitmap внутри операции запрещены.
4. Peer/session state, delivery progress, batch receipt, ChangeId identity, PendingApply, relay payload и tombstone — разные логические факты с независимыми retention horizons. Их можно физически группировать в транзакциях/сегментах, но нельзя смешивать в одну запись с общей максимальной жизнью.
5. Коалесцирование разрешено только до публикации. После durable freeze operation, ChangeId, Origin, payload и sequence неизменяемы.
6. WAL/v3 отвечает за crash recovery; provider feed/FLD Outbox — за ещё не опубликованные локальные изменения; BIN-SYNC Metadata Store — за опубликованные операции, receipts, delivery/ACK, dedup и relay. Не создавать второй PendingLocal/Pending journal с теми же фактами.
7. Storage — универсальный opaque byte engine/контракт, не знает о полях, HLC, peers и ChangeId. FLD Database — отдельная семантическая надстройка над Storage. Целевая поставка — две DLL: Fld1.Storage.dll и Fld1.Database.dll.
8. Старые wire/storage форматы не читаются, не мигрируются и не dual-write. Неизвестный/старый формат отклоняется fail-closed; требуется создание нового v3 store/namespace.
9. GC разделён на три независимых доказательства: Inbox receipts, ChangeId ledger, tombstones/ghosts. Payload ACK/compaction не является доказательством безопасности ни для одного из этих доменов.
10. ChangeId GC и tombstone/ghost GC остаются выключенными до реализации и тестирования всех доказательств из §§0.11–0.13.

## 0.1. Независимые координаты

- Origin — постоянное происхождение операции: author NodeId, author incarnation epoch и sequence, выделенный оригинальным автором.
- Issuer/transport peer — непосредственный отправитель текущего batch. При relay он не равен Origin author.
- OriginSequence — монотонная последовательность оригинального автора в пределах (scope, namespaceId, originAuthorNodeId). Она не сбрасывается при смене author epoch; allocator durable и защищён от rollback/clone.
- SenderCursor — последовательность конкретного отправителя/relay для конкретного получателя и author stream. Может иметь peer-relative offset и никогда не подменяет OriginSequence.
- StorageCommitId, WAL sequence, FLD JournalSeq и OutboxSeq — локальные storage/recovery координаты. Они не являются OriginSequence и не сравниваются между репликами.
- ChangeId — 128-bit operation identity, одинаковая на всех маршрутах. Не заменяется ни OriginSequence, ни SenderCursor.
- Published — операция прошла durable freeze и могла быть видна хотя бы одному sender/peer. После этого rewrite/coalesce запрещён.
- Current state — LWW/merge projection. Не является историей relay и не заменяет immutable operation journal.

## 0.2. Ownership: единственный владелец каждого факта

| Факт | Авторитетный владелец | Запрещённое дублирование |
|---|---|---|
| Crash recovery локальных транзакций | WAL / Storage engine | Второй recovery journal с тем же payload |
| Незавершённые локальные изменения | Durable provider feed / FLD Outbox / source journal | Отдельная BIN-SYNC PendingLocal-копия |
| Frozen published operation + Origin + ChangeId | BIN-SYNC Metadata Store (или один эквивалентный authoritative provider store) | Node checkpoint и FLD relay journal как независимые authoritative копии |
| Current field/record state, tombstone, ghost | Data Provider / FLD Database | Протокольная интерпретация в Storage engine |
| Per-peer/per-author delivery state | BIN-SYNC Metadata Store | ACK bitmap/recipient list в каждой операции |
| Batch retry receipt | BIN-SYNC Metadata Store | Полный payload в receipt |
| Global ChangeId dedup/equivocation | BIN-SYNC Metadata Store | Peer-scoped dedup как единственный источник истины |
| In-flight cross-store apply | Durable PendingApply intent + provider idempotency token | ACK до завершения durable apply |
| Physical storage atomicity | Storage engine | Притворная cross-store transaction |

Если provider и Metadata Store используют один Storage transaction domain, переход фиксируется атомарно. Если это разные хранилища, source feed остаётся unacked до durable freeze; retry использует тот же ChangeId и сверяет fingerprint/Origin. После подтверждения freeze feed ACK идемпотентен.

## 0.3. Каноническая модель опубликованной операции

PublishedOperation содержит: scopeId, namespaceId, ChangeId, canonical semantic fingerprint, originAuthorNodeId, originAuthorEpoch, originSequence, recordId, opKind, immutable payload или exact-version provider reference, HLC, keyEpoch и relayEligible.

Unique identity: (scopeId, namespaceId, ChangeId).
Одна identity имеет ровно один fingerprint и один Origin tuple.
Та же identity + тот же fingerprint + тот же Origin — duplicate/no-op.
Та же identity с любым другим fingerprint/Origin — equivocation; весь batch отклоняется до mutation.
Missing Origin никогда не выводится из issuer, relay cursor, HLC, OutboxSeq, JournalSeq или receipt cursor. Неизвестная provenance блокирует destructive GC.

## 0.4. Freeze и coalescing

1. До freeze provider feed/FLD Outbox хранит незавершённые локальные изменения. Для LWW_FIELD допускается один winner на canonical key (scope, namespace, record, field), выбранный полным protocol LWW order, а не временем прихода callback.
2. Record lifecycle и field state coalesce раздельно. Non-coalescible/audit operations не схлопываются.
3. Remote APPLY не должен стирать ещё не опубликованный local intent. Pending payload/reference живёт независимо от текущего LWW winner.
4. При freeze атомарно назначаются стабильные ChangeId, OriginAuthorEpoch, OriginSequence и immutable payload/reference; публикуется одна operation row. Sequence allocation и запись операции — одна durable transaction.
5. Sequence не выделяется до coalescing. Abort не должен создавать видимые дыры. Retry exact input возвращает тот же tuple и не создаёт второй operation.
6. После freeze payload и Origin неизменяемы, даже если operation не ACKed, уже отправлена, частично отправлена или ACK потерян. Последующие edits создают новые pending intents.

## 0.5. Per-peer delivery state: общая операция, независимый прогресс

Канонический ключ прогресса: (scopeId, peerNodeId, peerEpoch, namespaceId, originAuthorNodeId).
Минимальные факты: durable peer epoch/retirement fence; initial baseline generation/status; contiguous AckedCursor и PushedCursor; peer-relative SenderCursor offset; last batch digest-chain checkpoint; максимум одна immutable in-flight reservation на stream, если это требуется транспортом.

Операция не копируется на каждого peer. Delivery читает общую PublishedOperation и строит author-homogeneous batch. Per-peer state хранит только cursor/digest/reservation. Не вводить per-operation recipient array, ACK bitset или payload copy. Целевая кардинальность O(operations + peers × authorStreams), а не O(operations × peers).

Progress одного author stream можно упаковать в sparse row с presence mask, если ACK/pushed/offset/digest сохраняют независимые update semantics. Не объединять весь namespace в один mutable blob, который заставляет ACK одного peer переписывать состояние всех peers.

## 0.6. Wire v3: обязательная immutable provenance

- Protocol major строго 3. HELLO отклоняет major mismatch. Capability negotiation не может выключить обязательную provenance.
- Каждый DELTA_BATCH содержит ровно один resolved author stream.
- Immediate issuer/relay и его epoch остаются в batch header и определяют transport/session receipt identity.
- Каждая operation содержит обязательные поля: recordId:b128 | changeId:b128 | originAuthorEpoch:u32 LE | originSequence:u64 LE | opKind:u8 | payloadLen:canonical ULEB128 | payload:bytes. Durable author NodeId разрешается из authenticated ALIAS_MAP и сохраняется в storage в full b128 виде.
- Origin tuple = (resolvedAuthorNodeId, originAuthorEpoch, originSequence). OriginSequence > 0; epoch валиден по incarnation contract.
- OriginSequence строго возрастает внутри batch для данного author; gaps допустимы. Sequence назначается один раз original author и relay копирует byte-for-byte.
- Batch cursorStart/cursorEnd относятся только к sender's local contiguous delivery stream. Они не вычисляются из OriginSequence и не заменяют её. Direct-author fast path может проверить durable exact mapping, но не выводит provenance арифметически из peer-relative cursor/offset.
- Relay может назначить собственный sender cursor, но не меняет ChangeId, fingerprint, author, Origin epoch/sequence, HLC, key epoch или payload.
- RecordsRoot, BatchDigest и signature покрывают Origin fields. Любое изменение Origin на relay нарушает commitment.
- Нет optional provenance flags, v2/unflagged records, legacy parser или downgrade fallback.

## 0.7. Каноническое durable metadata v3

Логические категории (физическая группировка допустима только при сохранении атомарности и lifetime):
1. Published operation store — одна immutable operation/payload на ChangeId identity; local и relay-origin операции используют одну модель.
2. Global ChangeId identity/index — fingerprint + Origin + reference + relay/retention facts. Если PublishedOperation row переживает payload compaction и остаётся dedup authority, второй ledger row не создаётся. Если payload удаляется отдельно, остаётся одна компактная identity-only row.
3. PeerAuthorProgress — компактные per-peer/per-author cursors и digest/reservation facts.
4. InboxReceipt — issuer/epoch/ns/batch identity, complete header fingerprint, resolved author, sender cursor end, digest-chain checkpoint и данные для exact ACK. Payload операций не хранит.
5. PendingApply — exact inbound v3 batch intent и stable apply token до durable provider effect и receipt/progress finalization. Canonical PendingApply row encoding is format -7 and persists OriginAuthorEpoch/OriginSequence for every operation. Может ссылаться на immutable operation rows, если доказана lifetime.
6. CompletedApply — компактный idempotency token/result mapping; отдельный lifetime.
7. Membership/GC certificates and checkpoints — signed roster generation, member fences, per-member monotonic origin frontiers, forgotten frontier.
8. Provider publication intent — только если нужен recoverable cross-store handoff; не второй local change journal, удаляется после freeze+feed ACK.

Canonical BIN-SYNC Metadata partition identity begins with little-endian magic BMS3 plus exact scope length and UTF-8 scope. ChangeId identity values are fixed 45-byte v3 values (fingerprint[16], authorNodeId[16], authorEpoch[u32], originSequence[u64], localOutbound[u8]); this is the sole persisted Origin/identity authority for each ChangeId. Relay/outbound stream payload values are ChangeId[16] + payloadLength[i32] + payload (20-byte fixed overhead); they MUST NOT duplicate OriginAuthorEpoch/OriginSequence. On partition load, stream payload rows hydrate their immutable Origin from the already-loaded global ChangeId identity ledger without an additional Storage read; missing identity rows or mismatch between stream author and ledger author fail closed. Physical stream payload row kinds are 20 (relay) and 21 (outbound), and compaction MUST delete those exact kinds. Node WAL format is WAL/v3 and local mutation records persist OriginAuthorEpoch/OriginSequence. Any prior marker, pending-apply row encoding or WAL version is rejected, not upgraded. The durable provider-owned source feed has its own mandatory `BSP3` format marker at reserved provider key kind `0x25`; the active provider generation pointer is key kind `0x26`, and FULL_REPLACE staging manifests use key kind `0x41`. A fresh provider partition writes the marker and an empty active-generation id before any provider-owned data, a different/missing marker or active-generation pointer is rejected, and any existing provider-owned rows without the v3 marker fail closed. Current field and record-tombstone rows are scoped by the active generation id so a staged replacement is invisible until one atomic pointer switch. Each v3 LocalChange value is exactly canonical ProviderMutation bytes followed by one nonzero ChangeId[16]; readers MUST reject missing, zero, truncated or extra identity bytes and MUST NOT synthesize ChangeId during read/recovery. The marker and strict identity decoder are independent from BMS3 Metadata partition and WAL/v3 markers.

Source feed/FLD Outbox — единственная authority для unpublished edits. Metadata Store не создаёт параллельную PendingLocal таблицу с теми же изменениями.

## 0.8. Receipt, dedup и apply

- Receipt key: (scopeId, issuerNodeId, issuerEpoch, namespaceId, batchId). Issuer — immediate transport peer, не origin author.
- Authenticated transport-peer epoch хранится отдельно от originAuthorEpoch.
- Receipt содержит canonical header fingerprint и данные для повторного ACK после lost ACK. Тот же BatchId с другим committed header — failure.
- Global ChangeId ledger не зависит от issuer/route. Duplicate через alternate route не создаёт вторую relay operation.
- Весь batch preflight-валидируется: format, alias, Origin, monotonicity, ChangeId conflicts, payload schema, cursor continuity, digest/signature и provider acceptance. Нет partial mutation.
- При external provider apply PendingApply durable до provider mutation. Apply token idempotent; receipt, receive cursor и digest chain продвигаются только после durable provider success.
- Duplicate batch path проверяет receipt/header commitment и повторяет сохранённый ACK без повторного decode/apply/causal gate.
- Relay selection основан на first-seen valid operation/provenance, а не на победе LWW merge. LWW losers могут требовать relay.
- Peer-scoped SeenChanges недостаточен как единственная dedup authority.

## 0.9. Решения по минимизации метаданных

- Одна PublishedOperation/payload на ChangeId, общая для всех peers.
- Одна compact progress row на peer/author stream, не ACK row на каждую operation.
- Один compact receipt на batch, без payload.
- Одна global ChangeId identity/provenance fact, не per-route seen fact.
- Один PendingApply только пока external apply unresolved.
- Не дублировать relay payload, если relay delivery может ссылаться на общую immutable operation row. Если физическое разделение необходимо для compaction/indexing, payload bytes не копируются.
- CompletedApply хранит только idempotency token/result, не заменяет receipt или ChangeId ledger.
- Повторяющиеся author keys в ACK/pushed/offset maps объединять только при измеренном выигрыше.
- Replay reservations удалять атомарно с validated contiguous ACK, сохраняя digest-chain anchor.
- Receipt, ChangeId identity и tombstone имеют независимые horizons.

## 0.10. Retention domains

| Domain | Текущая политика v3 |
|---|---|
| Outbound/relay payload | Compact только через minimum safe contiguous ACK всех required peers/author streams и durable local consumer |
| Peer stream rows | Удалять только вместе с durable retired-through fence; максимум retired epoch сохранять |
| Replay reservations | Удалять только когда matching contiguous ACK покрывает reservation; digest anchor сохранять |
| Inbox receipts | Retire только с authenticated transport epoch fence + complete new initial-sync baseline + no unresolved PendingApply; atomic deletion |
| CompletedApply | Retain до отдельного provider retry/compaction proof |
| ChangeId ledger | GC disabled до signed roster + all-member monotonic OriginSequence frontier + reference scan |
| Tombstone/ghost | GC disabled до того же frontier + authoritative FULL_REPLACE generation + stale-member fence |
| Unknown/corrupt v3 state | Fail-closed; никогда не угадывать и не удалять |

## 0.11. Доказательство Inbox receipt GC

Receipt удаляется только если: (1) записан authenticated transport epoch; (2) зарегистрирована строго более новая incarnation; (3) complete initial-sync baseline новой incarnation durable committed для namespace; (4) monotonic retired-through fence блокирует retired/older/epoch-less sessions до ALIAS_MAP/data plane; (5) нет unresolved PendingApply/provider intent/apply token; любой старый outbound PendingBatch либо получил exact durable ACK, либо replacement baseline для того же author stream имеет тот же `IssuerEpoch` и покрывает абсолютный end cursor `old StreamOffset + PendingBatch.CursorEnd`; epoch-zero reservation всегда блокирует; (6) до retired-through fence stale epoch может только повторить/отметить pushed/ACK exact durable PendingBatch, но не резервировать новую batch; после fence запрещён и exact retry; (7) fence, peer progress retirement и receipt deletion атомарны; (8) restart на каждой границе оставляет либо старый receipt + допустимую старую эпоху, либо новый fence + удалённый receipt, но никогда допускаемую старую эпоху без receipt.

TTL, normal ACK, offline duration, digest advancement и merge snapshot сами по себе receipt GC не разрешают.

## 0.12. Доказательство ChangeId GC — пока запрещено

Identity row collectable только когда:
1. Origin tuple authenticated и immutable.
2. Namespace имеет authority-signed roster generation с canonical member set и monotonic generation.
3. Каждый member предоставляет authenticated signed monotonic contiguous applied-OriginSequence checkpoint для каждого author stream, bound к namespace, roster generation и snapshot generation.
4. Safe frontier per author — минимум contiguous applied OriginSequence по всем членам roster. Missing/offline/stale/unknown/regressive/invalidly signed member/checkpoint даёт frontier zero и блокирует GC.
5. Удаление member требует committed newer roster + durable epoch fence; rejoin требует FULL_REPLACE до incremental deltas.
6. ChangeId row ниже/equal safe frontier и нет PendingApply, operation payload, relay/outbound reservation, provider intent, snapshot pin или unresolved apply token reference.
7. GC checkpoint monotonic, signed, durable; deletion + checkpoint атомарны либо forgotten knowledge durably persisted first.
8. Replay ниже committed frontier отвергается, не принимается как новая operation.
9. Alternate-route, equivocation, restart и membership adversarial tests green.

Если хотя бы одно условие отсутствует — ChangeId row retain indefinitely. ACK payload, transport cursor, TTL, HLC age, storage pressure и GC_NOTICE доказательство не заменяют.

## 0.13. Доказательство Tombstone/Ghost GC — пока запрещено

Нужны все условия ChangeId GC и дополнительно:
1. Signed authoritative FULL_REPLACE namespace snapshot generation, отличающийся от merge SNAPSHOT_CHUNK.
2. Snapshot связывает consistent source snapshot token и provider change-feed tail watermark одной atomic barrier.
3. Все members текущего roster durably установили тот же generation/digest или более новый, доказывающий deletion.
4. Provider staging полной namespace image и atomic active-generation switch; destination-only stale rows удаляются replacement semantics. `StorageDataProvider` stages generation-scoped rows behind an inactive generation id, enforces contiguous canonical page order and unique record/field identities, verifies SHA-256 over `BIN-SYNC/FULL-REPLACE/v1 || generation[16 RFC-4122 network order] || sourceChangeFeedWatermark[u64le] || entryCount[i32le] || sorted ProviderMutation bytes`, and changes the active-generation pointer in one Storage transaction only after the complete image matches the manifest. Generation ids in the active pointer, generation-scoped row keys, session key and session manifest use the same canonical 16-byte RFC-4122 network order. The active pointer is key kind `0x26`; generation-scoped field/tombstone keys are `[kind][generation16][RecordId16][FieldId[u16be]]` (record tombstone omits FieldId); the session manifest is key kind `0x41` + generation16 and a fixed 85-byte value: version[u8], expectedCount[i32le], sourceFeedWatermark[u64le], digest[32], nextIndex[i32le], status[u8], baseGeneration[16], lastSortKey[19]. Abort removes staged rows in bounded batches. Old generations remain retained until a separate safe reclamation proof; an aborted staging generation never changes visible state. The caller MUST authenticate the authoritative roster/snapshot certificate, serialize the switch against apply, and prove no unresolved PendingApply/provider intent/relay reservation/snapshot pin can still depend on the old generation before invoking the provider capability; the provider API itself is not a membership authority.
5. Старое generation живёт до release всех readers/applies/snapshot pins; crash recovery выбирает ровно old или new generation.
6. Retired/fenced members не могут прислать old-generation delta; rejoin требует FULL_REPLACE.
7. Forgotten deletion frontier durable до physical tombstone/ghost deletion; frontier не может недооценивать forgotten history.
8. Field tombstone, record lifecycle tombstone и ghost semantics имеют отдельные adversarial tests.
9. Нет PendingApply, relay payload, operation identity или snapshot pin, которым tombstone ещё нужен.

Если доказательство неполное — tombstone/ghost retain indefinitely. TTL/HLC/GC_NOTICE/ordinary ACK/merge snapshot не разрешают purge.

## 0.14. Storage, FLD и две DLL

- Fld1.Storage.dll: domain-neutral engine — opaque byte keys/values, atomic batches, WAL/recovery, checksums, snapshots, manifests, ordered scans, storage-native commit IDs и safe generation reclamation. Не содержит BIN-SYNC/FLD types.
- Fld1.Database.dll: FLD schema, RecordId/FieldId, HLC, LWW/lifecycle, field/record tombstones, provider feed/Outbox, remote APPLY и FLD API; зависит от Storage.
- BIN-SYNC Core: wire/protocol, author/peer progress, ChangeId/Origin, receipts, dedup, relay, GC policy.
- BIN-SYNC↔FLD adapter зависит от нейтральных API; JournalSeq никогда не используется как OriginSequence.
- Третья Common DLL запрещена. Нет Storage→Database или Storage→BIN-SYNC dependency.
- Storage-only consumers не создают synthetic FLD fields, authors, HLC или Outbox rows.
- FLD Outbox/source feed владеет unpublished edits. WAL — recovery, не вторая semantic history. После freeze опубликованная operation/delivery принадлежит BIN-SYNC Metadata Store.

## 0.15. Clean-break и ошибки

Protocol major mismatch, missing Origin, zero/regressive OriginSequence, invalid alias, duplicate ChangeId in batch, equivocation, malformed v3 storage marker, truncated/corrupt row, unknown mandatory flags или unsupported required policy → fail closed.
Нет v2 parser, legacy storage reader, dual-write, implicit migration, fallback, downgrade или legacy public session API.
Старый partition нельзя открыть как пустой v3. Его можно только явно пересоздать либо обработать отдельным application-level export/import tool вне BIN-SYNC; tool не должен угадывать missing provenance.
Failed validation не вызывает partial mutation и ACK.

## 0.16. Release conformance и performance

Release требует golden wire/storage vectors; cross-implementation conformance; lost-ACK/restart exact replay; alternate-route dedup/equivocation; multi-hop Origin preservation; crash matrix на freeze, PendingApply, provider apply, receipt, ACK, snapshot switch и GC; malformed/old format rejection; requirement→test mapping; benchmark 500/10k/100k/1m operations и peer/author cardinality; bytes/op, bytes/(peer×author), mutation latency, allocation, compaction CPU. Оптимизация принимается только если correctness unchanged и целевой показатель реально лучше без существенной регрессии других метрик.

## 0.17. Историческая справка v2.4.22 (не нормативна)

Текст прежней спецификации сохранён ниже исключительно для traceability. Никакие v2.x wire/storage behavior не поддерживаются v3. Не реализовывать legacy paths по историческим примерам или формулировкам.

# 1. Обзор

BIN-SYNC CORE — компактный бинарный протокол для офлайн-первой синхронизации произвольных данных между узлами с произвольной топологией (клиент-сервер, P2P, mesh).

## 1.1. Цели

- **Детерминированная сходимость:** любые два узла, получившие одинаковый набор изменений, приходят к байт-идентичному состоянию.
- **Компактность:** минимум метаданных на запись, бинарный кодек, колоночные батчи, словарное сжатие.
- **Офлайн-первость:** узлы работают автономно неограниченно долго, синхронизируются при встрече.
- **Универсальность:** один транспорт и кодек для разнородных данных; разные сторы под разные модели.
- **Устойчивость к хаосу:** потерям, дубликатам, out-of-order, сбросам устройств, переводу часов.
- **Транспортная независимость:** работает через TCP, WebRTC, BLE, MQTT, файлы, QR-коды.
- **Безопасность:** поддержка E2EE с blind merge на недоверенных серверах.

## 1.2. Не-цели (границы применимости)

- Строгая (линеаризуемая) согласованность.
- Глобальные уникальные ограничения в офлайне.
- Реалтайм-совместное редактирование текста (требует отдельного CRDT-модуля поверх).
- Серверный поиск и фильтрация в E2EE-режиме (сервер становится dumb-хранилищем).
- Передача тяжелых блобов (BIN-SYNC синхронизирует только метаданные, сами файлы передаются через внешний Data Plane).
- Межзаписные транзакции между узлами (переводы, каскадные обновления). Атомарность батча [T1] не обеспечивает транзакционную семантику реляционной СУБД на уровне нескольких записей между узлами.

## 1.3. Модель согласованности

**Eventual Consistency with Pairwise FIFO / Single-Origin Causal Ordering:**

- **Внутри одной пары узлов** изменения доставляются строго в порядке создания (in-order per peer, namespace).
- **Внутри одного автора** изменения причинно упорядочены и не переупорядочиваются.
- **Глобальная сквозная причинность** (транзитивная между тремя и более узлами в mesh) **не гарантируется** по умолчанию.
- Для сценариев, требующих строгой каузальности, предусмотрен **опциональный** заголовок `causalDeps: array<b128>` (список `changeId` зависимостей), который приложение может использовать для принудительного порядка.

**Итог:** протокол гарантирует структурную идентичность состояния, но не глобальный happens-before порядок между разными источниками.

## 1.4. Философские границы (Манифест BIN-SYNC)

1. **Сходимость ≠ Смысловая корректность:** протокол гарантирует структурную идентичность, но не бизнес-валидность. Приложение использует Post-Merge Hooks для компенсации бизнес-ошибок.
2. **LWW — математический арбитр, не UX:** клиентский SDK сохраняет Shadow History для возможности отката «случайных» перезаписей.
3. **E2EE = Local-First:** режим blind merge ориентирован на персональные хранилища до 1–5 ГБ на устройство.
4. **GDPR = Crypto-Shredding:** мгновенное удаление данных достигается уничтожением ключа и заменой ciphertext на маркер SHREDDED с пересчётом дайджестов.
5. **Тяжелые блобы — вне протокола:** BIN-SYNC синхронизирует только BlobDescriptor, передача чанков делегируется внешним протоколам (HTTP Range, WebTorrent, IPFS).
6. **P2P LWW Poisoning:** в недоверенных mesh-сетях дефолтная политика меняется на MANUAL или SERVER_ARBITRATED.

# 3. Транспортная абстракция

## 3.1. Принцип

Протокольная сессия не открывает сокеты и не зависит от конкретного транспорта. `SyncSession` работает поверх `ISyncTransport`, который передаёт целые BIN-SYNC frames. TCP/TLS является одной из реализаций, а не частью общего протокольного слоя.

Разделение реализации .NET:
- `Sync/` — `SyncSession` и операции протокола (HELLO, batch/ACK, reconciliation, snapshot, IBLT, membership, schema, key rotation, fragmentation).
- `Transport/` — транспортные контракты и адаптеры.
- `Transport/Tcp/` — TCP listener и TLS host adapter; возвращает обычный `SyncSession`. Отдельного TCP-типа сессии нет.
- `Transport/Streams/` — адаптер `Stream` для TCP/TLS и других двунаправленных потоков.
- `Transport/InMemory/` — in-memory канал для тестов и embedded-host сценариев.

## 3.2. Контракт транспорта

`ISyncTransport` передаёт один полный пакет за вызов `SendAsync` и возвращает один полный пакет за `ReceiveAsync`. Частичные кадры, скрытая потеря, дублирование и переупорядочивание не допускаются, пока канал открыт. `MaxPacketSize` — предел полного пакета вместе с заголовком BIN-SYNC.

`SyncTransportCapabilities` явно объявляет гарантии доставки. `SyncSession.ConnectAsync` и `SyncSession.AcceptAsync` требуют одновременно `ReliableDelivery` и `OrderedDelivery`. Это необходимо, поскольку handshake и reconciliation обмениваются ожидаемыми последовательностями управляющих кадров.

```csharp
var (left, right) = PipeTransport.CreatePair();
var leftTask = SyncSession.EstablishAsync(localNode, left);
var rightTask = SyncSession.EstablishAsync(remoteNode, right);
await using var leftSession = await leftTask;
await using var rightSession = await rightTask;
```

Пользовательский транспорт реализует `ISyncTransport`, объявляет свои гарантии и передаёт полные frames. `IPeerAwareSyncTransport` — необязательное расширение для записи peer NodeId после HELLO.

Для established `SyncSession` используется один reader pump, который принимает полные кадры `ALIAS_MAP=0x03` и типов `0x04–0x13`, распределяет их по отдельным очередям по `FrameType`; ALIAS_MAP обслуживает отдельный control consumer, а остальные типы доступны ожидающим receive-операциям. Это позволяет одновременно выполнять receive-операции разных типов (например, `DELTA_BATCH`/`ACK` и `STATE_DIGEST`) без перехвата чужих кадров. Приёмы одного типа сериализуются: wire protocol пока не содержит correlation ID для нескольких одновременно активных запросов одного типа. Очереди ограничены; переполнение приводит к fail-closed `FLOW_CONTROL_VIOLATION`, а не блокирует общий reader pump и не задерживает доставку других типов. Raw fragment reassembly остаётся отдельным режимом и не смешивается с framed dispatch. Неизвестный тип, некорректная граница пакета или недопустимый кадр завершают receive pump с `FRAME_REJECTED`.

Для каждой пары NodeId допускается ровно одна активная протокольная сессия. Оба конца вызывают симметричный Connect/Accept-neutral метод EstablishAsync: каждый отправляет HELLO и получает HELLO другой стороны. Сторона с меньшим NodeId становится логическим инициатором и отправляет ALIAS_MAP после HELLO_ACK; сторона с большим NodeId отвечает HELLO_ACK и согласованной ALIAS_MAP. Сравниваются 16 байт NodeId в wire-порядке. Направление открытия TCP/WebRTC/другого транспортного канала не определяет протокольную роль.

Низший NodeId резервирует локальный слот (local Node instance, peer NodeId) после HELLO_ACK и удерживает его до DisposeAsync сессии, прежде чем отправить ALIAS_MAP. Высший NodeId резервирует свой слот после получения и проверки ALIAS_MAP инициатора, до отправки согласованной карты. Такой порядок исключает встречное удержание двух peer-locks. Повторные подключения той же пары ожидают освобождения слота; конкурентные сессии с одним peer запрещены, поскольку alias map и связанные cursors хранятся на уровне peer, а не transport connection. Отмена или ошибка handshake освобождает резервирование.

## 3.3. Требования к каналам

| Канал | Поддержка | Требования |
|---|---|---|
| TCP / TLS | Нативно | `StreamSyncTransport`, reliable + ordered |
| WebRTC DataChannel | Нативно при `ordered=true` и `maxRetransmits=null` | Reliable ordered messages |
| UDP | Через адаптер | Повторная передача, дедупликация, упорядочивание, фрагментация по MTU и congestion control |
| BLE / Wi-Fi Direct | Через адаптер | Надёжная упорядоченная доставка полных пакетов |
| MQTT / NATS / Kafka | Через адаптер | Сохранение packet boundaries и порядка в пределах одной сессии |
| Файлы / USB / QR | Отдельный import/export path | Не являются интерактивной `ISyncTransport`-сессией |

## 3.4. Самодостаточность кадров

Каждый кадр протокола:
- Начинается с магической сигнатуры `0x4253` ("BS").
- Содержит фиксированный 25-байтный заголовок.
- Содержит точную длину полезной нагрузки.
- Содержит контрольную сумму CRC32C.
- Не зависит от заголовков внешнего транспорта.
- Может быть сохранён в файл, передан по почте, записан в QR-код и восстановлен без потери семантики.

## 3.5. Файловая синхронизация (Sneakernet)

API движка:

```typescript
exportDelta(writer: WritableStream): Promise<void>
importDelta(reader: ReadableStream): Promise<void>
```

Дамп `DELTA_BATCH` кадров в бинарный файл. Импорт на изолированной реплике вызывает тот же `applyBatch()`, что и сетевое получение. Идентичность и идемпотентность сохраняются.

## 3.6. Управление потоком (Flow Control)

### 3.6.1. Для транспортов без встроенного backpressure

Для WebRTC DataChannel, BLE, сырых UDP:

- Стороны начинают передачу с начальным окном `INITIAL_WINDOW` (дефолт: 256 KB).
- Отправитель НЕ ИМЕЕТ ПРАВА отправлять кадры суммарным объёмом payload больше текущего остатка кредитов в `streamId`.
- Получатель по мере обработки данных и освобождения буферов отправляет кадр `WINDOW_UPDATE`.
- `WINDOW_UPDATE.credits` является **additive credit**: каждое значение увеличивает доступное окно отправителя на указанное число байт.
- Получатель НЕ МОЖЕТ увеличить окно выше `MAX_WINDOW_SIZE`.
- Отправитель обязан вести отдельный кредитный баланс для каждого `streamId`; контроль учитывает только байты payload, не 25-байтный frame header.
- Кредит расходуется при отправке кадра и возвращается получателем после того, как receive dispatcher забрал кадр из входной очереди; для фрагментов — после переноса тела во внутренний ограниченный reassembly buffer.
- Если payload логического кадра превышает начальный кредит окна, он передаётся как последовательность кадров `FLAG_FRAGMENT`; payload каждого физического фрагмента обязан укладываться в доступный кредит. Приёмник собирает исходный кадр до передачи его обработчику.
- Кадры с `streamId = 0` являются управляющими и не расходуют кредит.
- Сам `WINDOW_UPDATE` не расходует кредит, иначе обновление окна могло бы рекурсивно потребовать обновление окна.

### 3.6.2. Формат WINDOW_UPDATE

`WINDOW_UPDATE` имеет `streamId`, кредит которого увеличивается, `flags = 0` и payload ровно 4 байта: `credits: u32 LE`. Значение должно быть положительным. Обновление, которое увеличило бы баланс выше `MAX_WINDOW_SIZE`, является нарушением протокола и приводит к `FLOW_CONTROL_VIOLATION`. `frameSeq` — локальный строго возрастающий номер управляющего кадра в направлении сессии; получатель отклоняет нулевой, повторный или переставленный назад номер. Номер не используется для расчёта кредита. `credits` не может превышать число байт payload, ранее отправленных и ещё не подтверждённых обновлениями на этом потоке; незапрошенные кредиты отклоняются как `FLOW_CONTROL_VIOLATION`.

Flow Control включается только если обе стороны объявили capability `FlowControl` в HELLO/HELLO_ACK. Если capability не согласована, отправка и приём WINDOW_UPDATE запрещены, а обычные кадры не учитываются в кредитном окне.

### 3.6.3. Для транспортов со встроенным backpressure

Для TCP/TLS использование кадров `WINDOW_UPDATE` опционально (флаг `capabilities` в `HELLO`).

## 3.7. Мультиплексирование потоков (streamId ↔ namespaceId)

Поле `streamId: u32` в заголовке кадра связывается с `namespaceId` по назначению кадра:

| streamId | Назначение |
|---|---|
| `0x0000_0000` | Управляющий поток: Handshake, ALIAS_MAP, SCHEMA_MAP, MEMBERSHIP, Ping/Pong, GC_NOTICE |
| `0x0001_XXXX` | Поток namespace `XXXX`: STATE_DIGEST, NEED_RANGE, NEED_KEYS, DELTA_BATCH, SNAPSHOT_CHUNK, ACK, KEY_ROTATION, IBLT_REQUEST, IBLT_RESPONSE |

**Правила:**
- Управляющий поток (Control Plane) имеет **высший приоритет** над потоками данных.
- MEMBERSHIP и GC_NOTICE несут `namespaceId` в payload, но остаются управляющими кадрами: roster авторов/карантина относится к control plane, а namespace в payload ограничивает область применяемого cutoff/состояния.
- SCHEMA_MAP использует control stream, поскольку одна карта может содержать descriptors нескольких namespace.
- ACK обязан использовать тот же namespace stream, что и подтверждаемый DELTA_BATCH; отдельный диапазон stream ID для ACK не определён.
- WINDOW_UPDATE использует `streamId` потока, кредит которого обновляется; он не переводится на control stream.
- Управляющий поток использует только `streamId = 0`; namespace-кадр обязан использовать точное значение `0x0001_0000 | namespaceId`. Неизвестные/несогласованные значения отклоняются с `FRAME_REJECTED`.
- Каждый namespace синхронизируется **независимо**: отдельные курсоры, peer state, STATE_DIGEST.
- Ошибка в одном namespace (например, `NAMESPACE_FORBIDDEN`) завершает только соответствующий `streamId`, **не разрывая сессию** и не затрагивая другие namespace.
- Частичные сбои изолированы: отказ одного namespace не блокирует остальные.

# 4. Идентичность

## 4.1. Глобальные идентификаторы

```
nodeId    : 128-bit (UUIDv7 или crypto-random)
recordId  : 128-bit UUIDv7
changeId  : 128-bit (idempotency key)
batchId   : 128-bit
```

**Wire contract:** каждое поле b128 занимает ровно 16 байт. На публичной API-границе NodeId.From, RecordId.From, BatchId.From и Writer.B128(byte[]) нормализуют вход: длина 16 — без изменений; длина менее 16 — дополняется нулями справа; длина более 16 — берутся первые 16 байт BLAKE3("BIN-SYNC/AUTHID/v1" || input). Digest16.From требует ровно 16 байт. Нормализация — удобство API, а не альтернативный wire-формат.

## 4.2. Иерархия

| Уровень | Где живёт | Размер | Переиспользование |
|---|---|---|---|
| `nodeId` | Глобально, навсегда | 128 bit | Никогда |
| `internId` | Локально в реплике | 32 bit | Никогда для другого `nodeId` |
| `alias` | На проводе, в сессии | 16 bit | После каждого HELLO |

## 4.3. Alias map

При установке сессии стороны обмениваются:

```
ALIAS_MAP:
    0x0001 ↔ nodeId=0x7f3b... epoch=5
    0x0002 ↔ nodeId=0x9a2c... epoch=3
```

**Правила:**
- Алиас существует только в рамках одной сессии.
- При получении кадра с неизвестным `alias` → отвергнуть с `UNKNOWN_ALIAS`. Не угадывать.
- Переиспользование алиаса для другого `nodeId` или `epoch` внутри сессии запрещено.
- При reconnect алиасы перепривязываются заново.
- Между одной парой NodeId одновременно существует не более одной активной сессии; конкурентные transport connections к тому же peer должны ожидать освобождения сессионного слота.
- При симметричном EstablishAsync узел с лексикографически меньшим 16-байтовым NodeId является логическим инициатором, а узел с большим NodeId — отвечающей стороной. Оба конца отправляют HELLO; физическая сторона открытия транспорта роли не задаёт.
- Нижний NodeId резервирует слот перед отправкой ALIAS_MAP, верхний — после её получения и проверки; оба удерживают слот до закрытия SyncSession. Только после освобождения обоих слотов разрешено завершить следующий handshake и опубликовать новую alias map для этого peer.

### 4.3.1. Incremental ALIAS_MAP в установленной сессии

Handshake ALIAS_MAP остаётся полной таблицей на control stream. После handshake кадр типа `0x03` может нести incremental update, только если обе стороны объявили в HELLO capability `IncrementalAliasMap = 0x00000004`. Неизвестные capability bits игнорируются; отсутствие этого бита означает, что live update запрещён и при необходимости новой привязки сессия должна быть закрыта и установлена заново.

Форматы payload (все числа LE):

```
ALIAS_MAP_REQUEST {
    magic       : u8 = 0xA7
    kind        : u8 = 0x01
    requestId   : u32
    count       : u8 = 1
    entry {
        alias   : u16
        nodeId  : b128
        epoch   : u32
    }
}

ALIAS_MAP_RESPONSE {
    magic       : u8 = 0xA7
    kind        : u8 = 0x02
    requestId   : u32
    status      : u8   // 0 = accepted, 1 = rejected
    count       : u8   // 1 iff accepted, otherwise 0
    entry       : как в request, присутствует только при accepted
}
```

Оба варианта используют `FrameType=0x03`, `streamId=0`, `flags=0`; `requestId` ненулевой и является единственным correlation key. Чтобы встречные запросы не совпадали по ID, endpoint с меньшим wire-order NodeId выдаёт чётные requestId, endpoint с большим NodeId — нечётные; response повторяет ID запроса. При wraparound нулевой ID пропускается.

Отправитель сначала строит свободную привязку, но не публикует её в своей session map. Получатель проверяет endpoint epochs, уникальность alias и обратную привязку, затем атомарно применяет ровно одну запись и отправляет accepted response с той же записью. Отправитель атомарно применяет запись только после проверки коррелированного accepted response. Точная повторная привязка идемпотентна. Коллизия, epoch regression, mismatch ответа или rejected response приводят к fail-closed закрытию сессии; частичная карта запрещена. Если отмена произошла после того, как request мог попасть в транспорт, сессия закрывается: восстановление выполняется полным handshake ALIAS_MAP, а не продолжением с неопределённой картой.

Ни один DELTA_BATCH не может ссылаться на новый alias до accepted response. Если peer не объявил `IncrementalAliasMap`, отправитель не передаёт update и завершает попытку `UNKNOWN_ALIAS`, требуя reconnect/full handshake. Узел синхронизирует известную durable-author таблицу перед Node-owned push и выбранный author stream перед Metadata Store push; каждая сессия хранит собственную alias map.
## 4.4. Epoch реплики

Каждый `nodeId` имеет монотонный `epoch: u32`, инкрементируемый при:
- Сбросе устройства.
- Восстановлении из бэкапа.
- Явном «забыть» состояния (crypto-shredding).

При получении кадра с `remote.epoch < known.epoch[nodeId]`:
- Reject с `EPOCH_REGRESSION`.

## 4.5. Одна реплика — один логический участник

Запрещено двум процессам писать в один outbox с одним `nodeId` и `epoch`. Решения:
- Один лидер.
- Shared worker.
- Разные `nodeId` для разных процессов.

## 4.6. Модель авторства (authorship)

**Двухуровневая модель идентификации автора изменения:**

1. **`authorNodeId: b128`** — durable глобальный идентификатор узла, **создавшего** изменение (не ретранслятора). Хранится **всегда** в локальном хранилище.
2. **`origin: u16`** — сессионный alias автора в текущей парной сессии. Используется **только** на проводе для компактности.

**Правила резолва:**
- При создании записи локально: `authorNodeId = self.nodeId`, `origin` не нужен.
- При получении записи от пира: `origin` резолвится в `authorNodeId` через `ALIAS_MAP` и сохраняется локально.
- При ретрансляции через цепочку узлов (A → B → C): узел B **транслирует** `origin` для сессии B↔C, но `authorNodeId(A)` сохраняется в метаданных.
- **Tie-break ВСЕГДА** производится по `authorNodeId`, никогда по сессионному alias.

# 5. Время: HLC

## 5.1. Структура

```
HLC {
    wall     : u64     // микросекунды UTC с Unix epoch
    logical  : u32     // логический счётчик в рамках wall
    origin   : u16     // wire alias автора; НЕ участвует в tie-break
}
```

**Единица времени:** микросекунды UTC. Фиксирована в версии протокола. Клиент в миллисекундах умножает на 1000.

**Инвариант [C11]:** Поле `origin` в wire-формате `FieldWrite` и `FieldTomb` находится на фиксированном смещении **17** (байты 17–18). Смещение 15–16 занято младшими байтами `hlc.logical`. Запись по смещению 15 перезаписывает старшие 16 бит `hlc.logical`, превращая значение 1 в 65537 (0x00010001), что ломает детерминизм tie-break.

## 5.2. Tick-правила

### 5.2.1. Локальная генерация (send) с защитой от обратного хода часов

```
now = utc_now_µs()

if now > last.wall:
    wall = now
    logical = 0
elif now == last.wall:
    wall = last.wall
    logical = last.logical + 1
else:
    // Скачок системных часов назад (NTP, перевод времени, просыпание ОС)
    // Инвариант: HLC.wall ОБЯЗАН быть строго монотонным
    wall = last.wall
    logical = last.logical + 1

assert logical < 2^32 - 1, "Logical clock overflow"
last = (wall, logical)
```

### 5.2.2. Приём удалённого HLC (receive)

```
now = utc_now_µs()
wall = max(now, last.wall, remote.wall)

if wall == now and wall == last.wall and wall == remote.wall:
    logical = max(last.logical, remote.logical) + 1
elif wall == last.wall:
    logical = last.logical + 1
elif wall == remote.wall:
    logical = remote.logical + 1
else:
    logical = 0

last = (wall, logical)
```

## 5.3. Skew clamp

```
MAX_SKEW_µS = 60_000_000   // 60 секунд (конфигурируемо)

if remote.wall > now + MAX_SKEW_µS:
    reject frame with CLOCK_DRIFT
```

Clamp применяется только к `wall`. Идентичность не участвует.

## 5.4. Полный порядок (tie-break)

```
compare(a, b):
    if a.wall != b.wall:       return cmp(a.wall, b.wall)
    if a.logical != b.logical: return cmp(a.logical, b.logical)
    if a.authorNodeId.Lo != b.authorNodeId.Lo:
        return cmp_u64_le(a.authorNodeId.Lo, b.authorNodeId.Lo)
    return cmp_u64_le(a.authorNodeId.Hi, b.authorNodeId.Hi)

Lo — первые 8 wire-байт NodeId, интерпретированные как unsigned little-endian u64; Hi — следующие 8 байт. Этот порядок HLC tie-break отличается от лексикографического сравнения 16 wire-байт для выбора роли HELLO в §4.3. Неизвестный автор трактуется как нулевой NodeId и сортируется раньше ненулевого.
```

## 5.5. Использование

- LWW tie-break на уровне поля или записи.
- Сортировка конкурирующих операций.
- **НЕ** используется как глобальный курсор.

# 6. Канонический бинарный кодек

## 6.1. Примитивы

**Varint (ULEB128):** overlong-формы запрещены. Декодер отвергает с `INVALID_VARINT`.

**Фиксированные размеры:** `u8–u64`, `i8–i64` — little-endian; `b128`, `b256` — 16/32 байт.

**TLV:** `tag: u8, len: varint, value: bytes`.

**Строки:** `len: varint`, UTF-8 без BOM. Encoder не добавляет BOM и отвергает некорректные UTF-16 последовательности; decoder отвергает malformed UTF-8. Для совместимости decoder удаляет ровно один ведущий UTF-8 BOM.

**Массивы:** предваряются `count: varint`.

## 6.2. Структуры

- Поля в порядке возрастания `fieldId`.
- Дубликаты `fieldId` запрещены.
- Отсутствующие поля = отсутствие значения.

## 6.3. Числа с плавающей точкой

По умолчанию запрещены. Если схема разрешает: только IEEE 754. NaN reject с `INVALID_FLOAT`. `-0.0` → `+0.0`.

## 6.4. Время

`u64` микросекунд UTC.

## 6.5. Неизвестные поля

Сохраняются как raw TLV, входят в digest.

## 6.6. Детерминизм

**Инвариант [C1]:** два энкодера на одинаковых данных → байт-в-байт одинаковый результат.

# 7. Модель данных

## 7.1. Запись

```
Record = {
    recordId        : b128
    namespaceId     : u16
    state           : { fieldId -> FieldState }       // live values
    fieldTombs      : { fieldId -> FieldState }       // winning field tombstones
    lifecycleHlc    : HLC
    lifecycleAuthor : b128
    lifecycleValue  : u8           // 0x00=alive, 0x01=dead
    isDead          : bool         // вычисляемое: lifecycleValue == 0x01
}

FieldState = {
    value        : bytes
    hlc          : HLC
    authorNodeId : b128     // durable nodeId автора изменения поля
    keyEpoch     : u16      // crypto key epoch (0 when not encrypted)
}
```

## 7.2. Зарезервированные fieldId

```
0x0000       : LIFECYCLE (0=alive, 1=dead)
0x0001-0x00FF : системные
0x0100-0xFFFF : пользовательские
```

## 7.3. Операции над полями

### FieldWrite

```
FieldWrite {
    fieldId      : u16
    keyEpoch     : u16
    hlc          : HLC
    authorNodeId : b128
    value        : canonical bytes
}
```

Абсолютное значение поля. Не патч относительно базы.

### FieldTomb

```
FieldTomb {
    fieldId      : u16
    keyEpoch     : u16
    hlc          : HLC
    authorNodeId : b128
}
```

Помечает поле как удалённое. Значение tombstone в модели пустое; digest отдельно кодирует kind операции.

**Порядок FieldWrite / FieldTomb:** обе операции сравниваются по (wall, logical, authorNodeId) (§5.4). Более новый tombstone удаляет live-значение и становится текущим состоянием поля. Более старый tombstone не заменяет более новое live-значение. Запись снимает tombstone только если её полный HLC+author порядок строго выше; при равенстве tombstone выигрывает. Для одного fieldId остаётся не более одного победителя — live value либо tombstone.

## 7.4. Lifecycle (LWW; delete wins on an exact tie)

- `value = 0x00` → alive, `value = 0x01` → dead.
- Undelete только явным `FieldWrite(0x0000, hlc, 0x00)`.
- Поля с `hlc <= lifecycle.hlc` при `isDead=true` хранятся как **ghost**.
- Поля с `hlc > lifecycle.hlc` видны, но сущность считается удалённой до явного undelete.
- Пустой документ ≠ удалённая сущность.
- Lifecycle сначала сравнивается по (wall, logical, authorNodeId). Если полный ключ совпадает, но alive/dead конфликтуют, побеждает dead. Это точное tie-break правило, а не безусловное преимущество tombstone над операцией с более высоким author tie-break.
- Lifecycle FieldWrite использует fieldId 0x0000, keyEpoch=0 и ровно один байт value (0x00 или 0x01); FieldTomb для fieldId 0x0000 запрещён. Generic WriteField/TombField не принимают lifecycle field — используйте DeleteRecord/UndeleteRecord.

**Инвариант [D7]:** ghost-статус вычисляется по `field.authorNodeId` против `record.lifecycleAuthor`, не по `origin`.

## 7.5. RecordTombstone

Для `LWW_RECORD`: `{ recordId, hlc, authorNodeId }`.

## 7.6. Логические профили хранения

RowKVStore, FieldDocStore, CounterStore, SetStore, SeqStore, BlobStore — логические профили приложения. BinSync.Core 3.0.0 предоставляет общий Record с opaque byte payloads; специализированные runtime store-классы и typed CRUD API для этих профилей не входят в текущую реализацию.

# 8. Политики слияния

## 8.1. Регистрация

```
0x01 LWW_RECORD    0x06 SEQ_FRACTIONAL
0x02 LWW_FIELD     0x07 SEQ_CRDT
0x03 COUNTER_G     0x08 BLOB_REF
0x04 COUNTER_PN    0x09 MANUAL
0x05 SET_OR
```

### Профиль реализации BinSync.Core 3.0.0

Нормативная таблица выше описывает protocol-level policy IDs. Текущий runtime Node.ApplyBatch / ApplyBatchPayload поддерживает только LWW_FIELD (0x02); значение 0 принимается как legacy/default spelling того же LWW_FIELD. Любой другой policy code отклоняется с SCHEMA_MISMATCH, а не молча применяется как LWW.

MergeFieldWithPolicy, CRDT payload codecs и MergePolicyRegistry доступны как самостоятельные helper API, но MergePolicyRegistry не подключён к Node и не выбирает алгоритм в ApplyBatch. SchemaDescriptor.MergePolicy — metadata compatibility gate, а не runtime policy dispatcher. LWW_RECORD (0x01) и SEQ_CRDT (0x07) не реализованы в текущем runtime. MANUAL не предоставляет автоматический conflict workflow: FieldResolve (0x00FF) остаётся зарезервированным системным field ID без специальной обработки в ApplyBatch. MAX/MIN (0x81–0x84) — helper extensions, не wire policies runtime.

## 8.2. LWW_RECORD

Record-level discard разрешён.

## 8.3. LWW_FIELD (с подавлением кольцевого эха)

**Запрещён record-level discard.** Поддерживает **подавление кольцевого эха** [E2].

```
merge(local_fields, remote_fields):
    result = {}
    changed = false
    for each fieldId in union(local.keys, remote.keys):
        l = local.get(fieldId)
        r = remote.get(fieldId)
        if l and r:
            // Подавление эха: идентичная операция — no-op
            if l.hlc.wall == r.hlc.wall and 
               l.hlc.logical == r.hlc.logical and 
               l.authorNodeId == r.authorNodeId and 
               l.value == r.value:
                result[fieldId] = l
                continue  // changed остаётся false
            if compare(r.hlc, r.authorNodeId, l.hlc, l.authorNodeId) > 0:
                result[fieldId] = r
                changed = true
            else:
                result[fieldId] = l
        elif l:
            result[fieldId] = l
        else:
            result[fieldId] = r
            changed = true
    
    result_lifecycle = merge_lifecycle(local.lifecycle, remote.lifecycle)
    return (result, result_lifecycle, changed)
```

**Правило применения в антиэнтропии:**

```
applyFieldWrite(recordId, fieldId, fieldOp):
    local = storage.get(recordId)
    localField = local.get(fieldId)
    
    // Проверка идентичности (подавление эха)
    if localField and 
       localField.hlc == fieldOp.hlc and 
       localField.authorNodeId == fieldOp.authorNodeId and 
       localField.value == fieldOp.value:
        return { changed: false }
    
    merged, changed = policy.merge(local, fieldOp)
    if changed:
        storage.put(recordId, merged)
        updateBucketDigest(recordId, local, merged)
    return { changed }
```

**Инвариант [E2]:** Если входящая операция идентична локальной версии (`hlc`, `authorNodeId`, `value` совпадают), узел возвращает `changed = false` и **не добавляет** операцию в `outbox`. Это предотвращает Broadcast Storm в кольцевых топологиях (A → B → C → A).

## 8.4. COUNTER_G

Для каждого автора: `result[author] = max(local, remote)`.

**Wire payload:** `count: varint | (author: b128 | value: u64 LE)*`.
- `count` — количество компонентов; до выделения памяти/итерации проверяется, что все записи могут находиться в оставшемся payload.
- `author` — 16 байт; компоненты строго упорядочены по возрастанию unsigned-лексикографического порядка байтов. Повтор автора запрещён.
- После последнего компонента обязателен EOF. Лишние байты запрещены.
- Encoder нормализует author в b128 и отвергает коллизии, возникшие после нормализации.

## 8.5. COUNTER_PN

Положительный и отрицательный счётчики сливаются покомпонентно. `value = sum(positive) - sum(negative)`.

**Wire payload:** `positiveMap | negativeMap`, где каждая map имеет формат COUNTER_G: `count: varint | (author: b128 | value: u64 LE)*`.
- Каждая из двух map независимо сортируется по author в строго возрастающем unsigned-лексикографическом порядке; повтор автора внутри одной map запрещён. Один author может присутствовать одновременно в positive и negative map.
- После второй map обязателен EOF.
- Вычисление signed `value` должно обнаруживать переполнение `Int64`, а не выполнять wraparound.

## 8.6. SET_OR (Observed-Remove)

Выжившие элементы — все элементы с add-dot, не покрытым remove-dot. Dot идентифицируется парой `(actor: b128, seq: u64)`; один add-dot не может обозначать более одного элемента.

**Wire payload:**
```
addCount: varint |
  (element: Bytes | actor: b128 | seq: u64 LE)* |
removeCount: varint |
  (actor: b128 | seq: u64 LE)*
```
- Adds строго упорядочены по `(element bytes, actor bytes, seq)`; remove-dots — по `(actor bytes, seq)`. Сравнение byte strings — unsigned-лексикографическое.
- Add-dot и remove-dot внутри соответствующего списка должны быть уникальны; дубликаты и неупорядоченные записи запрещены.
- Counts проверяются до выделения коллекций по минимальному размеру записи и оставшемуся payload; после последнего remove-dot обязателен EOF.

## 8.7. SEQ_FRACTIONAL

Полный порядок: `(parentId, orderKey, authorNodeId, seq)`.

**Wire payload:** `parentId: b128 | orderKey: UTF-8 String | authorNodeId: b128 | seq: u64 LE | value: Bytes`.
- `orderKey` сравнивается по unsigned-лексикографическому порядку UTF-8 bytes (эквивалентно порядку Unicode scalar values); locale-dependent и UTF-16 code-unit сравнение запрещены.
- Декодер обязан потребить payload полностью.
- Равная tuple identity означает одну и ту же запись. Если две такие записи несут разные `value`, payload конфликтует и должен быть отклонён; выбирать локальный operand запрещено.

## 8.8. BLOB_REF

Иммутабельна. «Изменение» = новый `blobId`.

**Wire payload:** `blobId: b128 | size: u64 LE | contentType: UTF-8 String | hash: b256`. Нулевой `hash` означает отсутствие известного хэша содержимого.
- Декодер обязан потребить payload полностью.
- Один `blobId` однозначно идентифицирует неизменяемый descriptor: одинаковый ID с различающимися `size`, `contentType` или `hash` является конфликтом и отклоняется.
- При разных `blobId` для детерминированного слияния побеждает лексикографически больший b128 ID; сравнение выполняется по unsigned bytes.

## 8.9. MANUAL (с FieldResolve)

Приложение разрешает конфликт через `FieldResolve` (системное поле `0x00FF`).

# 9. Digest и бакеты

## 9.1. Record digest

```
recordDigest = BLAKE3-256(
    domainTag("BIN-SYNC/RECORD/v2") ||
    recordId ||
    sort_by_fieldId_then_kind(FieldDigestPayload*) ||
    LifecycleDigestPayload
)
```

### 9.1.1. Инвариант дайджеста для зашифрованных полей

В режиме E2EE дайджест вычисляется по сырому шифротексту. Повторное шифрование запрещено. [G5].

### 9.1.2. Точная формула FieldDigestPayload

```
FieldDigestPayload:
    fieldId      : u16 LE      // 2 bytes
    kind         : u8          // 0=FieldWrite, 1=FieldTomb
    keyEpoch     : u16 LE      // 2 bytes
    wall         : u64 LE      // 8 bytes
    logical      : u32 LE      // 4 bytes
    authorNodeId : b128        // 16 bytes (DURABLE, НЕ origin!)
    valLen       : varint      // 1-10 bytes
    valueBytes   : bytes       // valLen bytes

Итого: 33 + varint + valLen байт на поле. Сортировка — (fieldId, kind); kind обязателен даже для пустого значения.

### 9.1.3. Точная формула LifecycleDigestPayload

Фиксированно 34 байта (включая `lifecycleAuthor`).

### 9.1.4. StateRootDigest

```
StateRootDigest = BLAKE3-256(
    domainTag("BIN-SYNC/STATE/v2") ||
    namespaceId || recordCount ||
    sort_by_prefix_then_recordId(all BucketDigest canonical encodings)
)

Legacy OutboxCursor в кадре STATE_DIGEST зарезервирован и передаётся как zero; он не входит в StateRootDigest. Для reconciliation peers должны использовать один digest profile; смешивание v2.4.11/v2.4.12 record digest несовместимо.
```

## 9.2. Bucket digest

- `bucket_key = BLAKE3-256(recordId)`.
- Динамическое ветвление (`bucketRadixBits`: 8/12/16).
- Инкрементальное обновление: `count ± 1, xor ^= digest, sum ± digest`.
- Bucket Rollup для разной глубины.
- Range-split внутри hash-prefix.

# 10. Журнал изменений

## 10.1. Outbox

```
OutboxEntry {
    namespaceId    : u16
    seq            : u64    // монотонный per (authorNodeId, namespaceId)
    changeId       : b128
    recordId       : b128
    opKind         : u8
    payload        : canonical bytes
    causalDeps     : array<b128>   // опционально
    createdAt      : u64 (µs UTC)
    authorNodeId   : b128
}
```

## 10.2. Inbox

```
InboxReceipt {
    namespaceId      : u16
    issuerNodeId     : b128
    issuerEpoch      : u32
    batchId          : b128
    durableAuthor    : b128
    cursorEnd        : u64
    headerFingerprint: b128
    appliedAt        : u64   // HLC wall, Unix microseconds
    expiresAt        : u64   // 0 = expiry is not scheduled
}

**Ключ идемпотентности:** `(issuerNodeId, namespaceId, issuerEpoch, batchId)`.

**Компактное receipt-представление:** `cursorStart` не хранится отдельным полем: он, как и `cursorEnd`, `prevBatchDigest`, `recordsRoot` и `batchDigest`, committed в `headerFingerprint`. Fingerprint — BLAKE3-128 с domain `BIN-SYNC/INBOX-RECEIPT/v1` над namespace, issuer, epoch, batchId, cursorStart/end, prevBatchDigest, recordsRoot, batchDigest, schemaId, schemaVersion, mergePolicy и flags (кроме transport-only бита causal trailer). Он не включает entry payload и causal dependency trailer.

Для legacy state v3-v7 `headerFingerprint` и сохранённый `cursorEnd` могут отсутствовать; такой receipt явно помечается как legacy-unknown и сохраняет прежний duplicate-ACK behavior. Новые receipts всегда содержат оба поля. `expiresAt=0` означает, что срок удаления ещё не назначен; GC не может трактовать ноль как истёкший срок.

### 10.2.1. Inbox GC

`expiresAt` — только advisory time field и не является самостоятельным разрешением на удаление. TTL, обычный ACK, последующий batch, snapshot или локальное истечение времени сами по себе не доказывают безопасность reclamation.

**Storage-backed исключение E-26:** Inbox receipt может быть удалён только вместе с durable retired-through fence authenticated transport-peer epoch, когда более новая peer incarnation зарегистрирована и её complete initial-sync baseline durably committed. Retirement блокируется любым unresolved PendingApply для peer/namespace, включая legacy intent с неизвестным transport epoch. Receive path после fence отклоняет retired и epoch-less traffic. Receipt с неизвестным transport epoch сохраняется до exact authenticated duplicate от зарегистрированной текущей эпохи, который атомарно re-attributes receipt. Active-epoch receipts и CompletedPendingApply tokens сохраняются.

Вне этого узкого E-26 storage lifecycle receipt GC выключен; новые receipts используют `expiresAt=0`. Старый receipt нельзя удалить по времени, ACK, cursor, digest-chain advancement или snapshot без retired-epoch fence. Это не wire-level expiry и не разрешение на произвольную compaction.

### 10.2.2. Потерянный ACK

1. B применил batch и атомарно сохранил InboxReceipt, затем отправил ACK.
2. ACK потерян.
3. A по таймауту повторно шлёт тот же `batchId`.
4. B проверяет receipt по ключу `(issuerNodeId, namespaceId, issuerEpoch, batchId)`.
5. Если headerFingerprint известен и отличается от receipt, B отклоняет повтор как `BATCH_TRANSACTION_FAILED`; если совпадает — повторяет ACK с сохранёнными `cursorEnd` и `durableAuthor`.
6. Entry payload, replay-supplied ChangeIds и causal dependencies на duplicate path не декодируются/не применяются; duplicate обязан обходить causal gate. Изменённый payload при неизменном BatchId и неизменном header commitment игнорируется как повтор, а не применяется.
7. Для legacy-unknown receipt без headerFingerprint сохраняется прежнее поведение: batch считается duplicate, но conflicting-header validation до миграции невозможна.

`appliedAt` фиксирует HLC wall time принятия. `expiresAt=0` запрещает TTL-based expiry. StorageMetadataStore может reclaim receipt только по E-26; все остальные receipts удерживаются.

## 10.3. Peer state

Peer membership/session state и author-stream progress — разные координаты:

```
PeerSession {
    peerNodeId, peerEpoch, namespaceId
    initialSyncComplete, membershipEpoch, lastSeen
}

PeerAuthorStream {
    peerNodeId, peerEpoch, namespaceId, authorNodeId
    ackedCursor, pushedCursor, localStreamOffset
    lastBatchDigest
    pendingImmutableBatch?   // at most one unacknowledged reservation
}

ReceiveAuthorStream {
    senderNodeId, senderEpoch, namespaceId, authorNodeId
    lastReceivedSeq
}

ReceiveDigestChain {
    senderNodeId, senderEpoch, namespaceId
    lastBatchDigest
}
```

Peer/session membership is not a substitute for author-specific cursors. A shared Outbox sequence is local and immutable; the peer's wire cursor is derived from its own ACK plus the proven local stream offset. A reservation is durable before send and is released only by its matching pushed ACK.

## 10.4. Range cursor

Изменения одного author stream от одного пира применяются строго в порядке `[cursorStart .. cursorEnd]`.

**Инвариант [S2]:** `cursorStart == lastReceivedSeq(sender, epoch, namespace, authorStream) + 1`.

## 10.5. Коалесцирование

Батч покрывает непрерывный диапазон `[ackedCursor+1 .. currentPeerCursor]` только для одного author stream. Нельзя объединять курсоры разных авторов в один scalar.

## 10.6. Резолв authorNodeId

Compact mode: `origin` → `authorNodeId` через `ALIAS_MAP`. Unknown → reject `UNKNOWN_ALIAS`.

# 11. Membership и GC

## 11.1. Membership

Приоритет: `LEFT > SUSPENDED > ACTIVE`.

## 11.2. Watermark

Safe retention is calculated independently for every `(namespaceId, authorNodeId)` stream:

```
safeOutboxSeq[author] =
    min(peer.ackedCursor[author] + peer.localStreamOffset[author])
    over every durably interested peer whose initialSyncComplete baseline is committed
```

An absent peer-stream row, unknown membership baseline, stale/unretired epoch or incomplete snapshot/feed barrier contributes zero and fails closed. A new peer joins the retention set only after its complete baseline is durably committed. A retired peer is excluded only after its old epoch is durably fenced. No interested-peer proof means no positive safe prefix.

## 11.3–11.4. Новый/ушедший член

Новый не блокирует GC. Ушедший исключается из min.

## 11.5. Tombstone retention and GC safety

`TOMBSTONE_MIN_TTL` (7 дней по умолчанию) задаёт только минимальный возраст, после которого tombstone может стать кандидатом на reclamation. TTL **не является** доказательством того, что tombstone больше не нужен.

Удаление field tombstone, record lifecycle tombstone или ghost state запрещено, пока одновременно не выполнены все условия:

1. Для namespace существует durable safe frontier, который покрывает tombstone и все более ранние операции всех известных author streams. Frontier должен быть основан на непрерывных per-author stream positions, а не только на wall clock.
2. Каждый peer текущего membership baseline подтвердил применение согласованного snapshot/delta baseline, включающего этот frontier. Peer без подтверждённого состояния блокирует reclamation.
3. Peer, исключённый из baseline, quarantined/fenced и не может продолжить incremental DELTA_BATCH со старым состоянием. Перед возобновлением delta он обязан пройти полный snapshot/resync, который восстанавливает tombstones/ghosts и HLC baseline.
4. Новый peer начинает с полного snapshot; он не может использовать произвольный старый cursor как доказательство актуальности.
5. Snapshot и feed watermark связаны одной атомарной barrier. Snapshot current-state rows не заменяет relay/event history и не может самостоятельно продвинуть Outbox/relay ACK.

Один scalar HLC wall cutoff недостаточен: он не доказывает, что peer получил конкретный tombstone или что все author streams закрыли диапазон старых операций. Поэтому `GC_NOTICE.TombstoneCutoffWall` является advisory hint и не разрешает локальное удаление. `WatermarkGate` — только сравнивающий primitive; пока durable cutoff не хранится и gate не вызывается до всех incremental apply/snapshot paths, он не считается включённой защитой.

**Текущее безопасное поведение:** tombstone/ghost GC выключен (fail-closed). `PurgeBelowCutoff` не удаляет ни обычные live fields, ни field tombstones, ни record lifecycle tombstones. Возраст, LastSeen и GC_NOTICE не должны обходить это правило.

## 11.8. Карантин долгих узлов (Tombstone Cutoff Policy)

После введения durable safe frontier peer, чьё подтверждённое namespace baseline ниже frontier, переводится в `QUARANTINE_RESYNC`. Пока полный resync не завершён, его incremental DELTA_BATCH отклоняется с `OUTDATED_WATERMARK`/`SNAPSHOT_REQUIRED`. Само значение `lastSeen < cutoffWall` может инициировать проверку/карантин, но не заменяет проверку durable stream frontier и не является самостоятельным доказательством stale state.

**Инвариант [D6]:** Узел не может применить операцию, способную воскресить состояние, tombstone которого был безопасно reclaimed. До выполнения safe-frontier и full-resync условий tombstone сохраняется.

# 12. Wire-формат

## 12.1. Магическая сигнатура

`0x42 0x53` ("BS").

## 12.2. Frame (25 байт заголовка)

```
Frame {
    magic      : u16 = 0x4253     // 2 bytes
    version    : u8  = 0x00       // 1 byte
    frameType  : u8               // 1 byte
    flags      : u8               // 1 byte
    streamId   : u32              // 4 bytes
    frameSeq   : u64              // 8 bytes
    payloadLen : u32              // 4 bytes
    crc32c     : u32              // 4 bytes
    payload    : bytes
}
```

### 12.2.1. Контроль целостности кадра

- `magic != 0x4253` → silent drop.
- `payloadLen > MAX_PAYLOAD_SIZE` → `PAYLOAD_TOO_LARGE`, сессия разрывается.
- `CRC32C` mismatch → `CORRUPTED_FRAME` (0x0015), сессия сохраняется.

### Флаги

```
bit 0: COMPRESSED (zstd)
bit 1: SIGNED (Ed25519)
bit 2: FRAGMENT
bit 3: ENCRYPTED (E2EE)
```

## 12.3. Системные лимиты (Hard Limits)

```
HEADER_SIZE          : 25 байт
MAX_FRAME_SIZE       : 16 MB
MAX_PAYLOAD_SIZE     : 16 MB - 25 bytes
MAX_FIELD_VALUE_SIZE : 4 MB
MAX_RECORDS_PER_BATCH: 10 000
MAX_WINDOW_SIZE      : 16 MB
MAX_LOGICAL_MESSAGE  : 256 MB
```

## 12.4. Zstd Bomb Guard

`uncompressedLen` в первых 4 байтах payload. Reject при `> MAX_FRAME_SIZE`.

## 12.5. Фрагментация

```
FragmentEnvelope {
    messageId       : b128
    fragmentIndex   : u32 LE
    fragmentCount   : u32 LE
    totalMessageLen : u64 LE
    fragmentLen     : u32 LE
    fragmentBytes   : bytes
}
```

## 12.6. Типы кадров

0x01–0x13 (HELLO, HELLO_ACK, ALIAS_MAP, SCHEMA_MAP, MEMBERSHIP, STATE_DIGEST, NEED_RANGE, NEED_KEYS, DELTA_BATCH, SNAPSHOT_CHUNK, ACK, GC_NOTICE, ERROR, WINDOW_UPDATE, PING, PONG, KEY_ROTATION, IBLT_REQUEST, IBLT_RESPONSE).

Канонические значения: `DELTA_BATCH=0x09`, `SNAPSHOT_CHUNK=0x0A`, `ACK=0x0B`, `GC_NOTICE=0x0C`, `KEY_ROTATION=0x11`, `IBLT_REQUEST=0x12`, `IBLT_RESPONSE=0x13`. Реализации MUST использовать эти отдельные значения. Ранее встречавшиеся внутренние коллизии `GC_NOTICE/ACK` и `IBLT/DELTA_BATCH` являются ошибками реализации, а не допустимыми вариантами wire format.

Established `SyncSession` использует единственный reader pump и маршрутизирует полные кадры `ALIAS_MAP=0x03` и `0x04–0x13` по FrameType. ALIAS_MAP request/response потребляет отдельный control consumer; остальные кадры направляются в отдельные bounded queues. Параллельные операции разных типов могут принимать кадры независимо. Ожидающие приёмы одного типа сериализуются, поскольку wire protocol не содержит correlation ID для нескольких одновременно активных запросов одного типа (исключение — ALIAS_MAP, у которого есть requestId). Raw fragment reassembly остаётся отдельным режимом и не смешивается с framed dispatch.

## 12.7. HELLO

FrameType `0x01`, control stream `0`, flags `0`. Payload ровно 26 байт:

```
HELLO {
    nodeId        : b128
    epoch         : u32 LE
    protocolMajor : u16 LE = 3
    capabilities  : u32 LE
}
```

Canonical implementation sequence number is `1`. A receiver MUST reject any payload whose length is not exactly 26 bytes, any `protocolMajor != 3`, invalid frame type/stream/flags, or epoch outside the supported signed 32-bit incarnation range. Unknown capability bits may be ignored; no capability can disable mandatory v3 provenance.

## 12.8. HELLO_ACK

FrameType `0x02`, control stream `0`, flags `0`. Payload has the exact same 26-byte layout as HELLO, with `protocolMajor = 3`; canonical implementation sequence number is `2`. HELLO_ACK is not interchangeable with HELLO. A receiver MUST apply the same length, major-version, frame and epoch validation.

## 12.9–12.16. ALIAS_MAP, SCHEMA_MAP, MEMBERSHIP, STATE_DIGEST, NEED_RANGE, NEED_KEYS, IBLT, KEY_ROTATION

Стандартные LE-раскладки. Established-session ALIAS_MAP update использует payload и правила §4.3.1. HELLO capability bit `0x00000004` означает поддержку этих request/response кадров.

## 12.17. DELTA_BATCH

```
DELTA_BATCH {
    namespaceId     : u16 LE
    schemaId        : u16 LE
    schemaVersion   : u16 LE
    mergePolicy     : u8
    flags           : u8
    issuerNodeId    : b128
    issuerEpoch     : u32 LE
    cursorStart     : u64 LE
    cursorEnd       : u64 LE
    recordCount     : varint
    batchId         : b128
    prevBatchDigest : b128
    recordsRoot     : b128
    batchDigest     : b128
    records         : bytes  // count varint, then recordId b128 | changeId b128 | opKind u8 | payloadLen varint | payload
}
```

### 12.17.0. Каноническая запись и provenance

Каждая запись массива `records` имеет фиксированный 32-байтовый префикс: `recordId` (b128), затем исходный `changeId` (b128), затем `opKind` (u8), `payloadLen` (varint) и `payload`. `changeId` обязателен и сохраняется без изменения при ретрансляции через любое число узлов. Нулевой `changeId` запрещён для исходящих DELTA_BATCH; при приёме нулевой идентификатор отклоняется как `BATCH_TRANSACTION_FAILED`. `recordsRoot` вычисляется по полному каноническому массиву, включая `changeId`; следовательно, `batchDigest` и подпись автоматически связывают provenance. Поле `opKind` обязано совпадать с wire tag операции в `payload` (`0x01` FieldWrite, `0x02` FieldTomb, `0x03` RecordTombstone); несовпадение отклоняется до staging/commit. Для `RecordTombstone` вложенный `recordId` обязан совпадать с envelope `recordId`; несовпадение также отклоняется до commit. Это правило одинаково применяется к DELTA_BATCH и snapshot batches.

## 12.17.1. Атомарность

[T1] Батч либо применяется целиком, либо не применяется.

### 12.17.2. Batch digest chain

```
chain = (issuerNodeId, namespaceId, issuerEpoch)
first: prevBatchDigest = 0x00...00
batchDigest = BLAKE3-128(domainTag || batchId || namespaceId || ...)
```

## 12.18. SNAPSHOT_CHUNK

`SNAPSHOT_CHUNK` передаёт полный LWW-срез записи: `recordId`, список полей и явное состояние lifecycle. Каждая строка поля содержит `fieldId`, `isTombstone` (u8: 0 — значение, 1 — tombstone), HLC, `authorNodeId`, `keyEpoch` и значение (пустое для tombstone). После списка полей передаётся `hasLifecycle` (u8: 0/1), `lifecycleValue`, lifecycle HLC и `lifecycleAuthor`. Поля-tombstone и lifecycle применяются через те же LWW merge primitives, что и DELTA_BATCH, без создания локальных Outbox entries. Неинициализированный lifecycle (`hasLifecycle=0`) не применяется.

`ChunkIndex` должен быть меньше `ChunkCount`; нулевой `ChunkCount` запрещён. Snapshot разбивается на `ChunkCount = max(1, ceil(recordCount / maxRecords))` чанков с индексами `0..ChunkCount-1`. Все чанки одного transfer строятся из одного согласованного копирования состояния под общей блокировкой Storage → Outbox → Meta; сетевую отправку выполняют уже после освобождения блокировок. Получатель требует chunk 0 первым, затем строго последовательные индексы с одинаковыми NamespaceId и ChunkCount. Пропуск, повтор, перестановка или несовпадение метаданных чанков отклоняются. Обрыв до последнего чанка не считается успешным завершением snapshot.

Последний чанк содержит `SnapshotTail` (80 байт): `snapshotDigest`, `snapshotStateDigest`, `outboxCheckpointDigest`.

## 12.19. ACK

Содержит `batchId` подтверждаемой транзакции.

## 12.20–12.22. GC_NOTICE, WINDOW_UPDATE, PING/PONG

Стандартные LE-раскладки. `GC_NOTICE.TombstoneCutoffWall` — advisory metadata only: при текущей редакции протокола оно не авторизует удаление tombstone/ghost. Получатель может использовать его для оценки stale-peer состояния, но обязан сохранить все tombstones до выполнения §11.5 safe-frontier и full-resync условий.

## 12.23. ERROR

Коды ошибок: `UNKNOWN_ALIAS` (0x0001), `EPOCH_REGRESSION` (0x0002), `CLOCK_DRIFT` (0x0003), `INVALID_VARINT` (0x0004), `INVALID_FLOAT` (0x0005), `SCHEMA_MISMATCH` (0x0006), `SEQ_GAP` (0x0007), `DUPLICATE_BATCH` (0x0008), `NAMESPACE_FORBIDDEN` (0x0009), `INTERNAL` (0x000A), `OUTDATED_WATERMARK` (0x000B), `DECOMPRESSION_LIMIT_EXCEEDED` (0x000C), `BATCH_TRANSACTION_FAILED` (0x000D), `PAYLOAD_TOO_LARGE` (0x000E), `FLOW_CONTROL_VIOLATION` (0x000F), `UNKNOWN_KEY_EPOCH` (0x0010), `SCHEMA_PENDING` (0x0011), `CAUSAL_DEP_MISSING` (0x0012), `SIGNATURE_INVALID` (0x0013), `TRUST_REVOKED` (0x0014), `CORRUPTED_FRAME` (0x0015), `FRAME_REJECTED` (0x0016), `BATCH_CHAIN_BROKEN` (0x0017), `ACK_OUT_OF_RANGE` (0x0018), `SNAPSHOT_REQUIRED` (0x0019).

## 12.24. Байтовая раскладка операций

### 12.24.1. ASCII-диаграмма FieldWrite

# 13. Протокол синхронизации

## 13.1. Лестница reconcile

```
cursor → prefix buckets → range split → IBLT → snapshot + tail
```

## 13.2. Фазы сессии

Handshake → Discovery → Reconcile → Transfer → GC.

## 13.3. Алгоритм выбора стратегии

Стандартный дифф по дайджестам, фолбэк на `NEED_RANGE` или `SNAPSHOT + tail`.

## 13.4. Применение изменений (критический порядок проверок)

**КРИТИЧНО:** Проверка идемпотентности выполняется **ДО** проверки `prevBatchDigest`. Это исключает ложные отказы при повторной доставке после потерянного ACK.

```
applyBatch(batch):
    // ШАГ 1: Проверка идемпотентности (ПЕРЕД проверкой цепочки!)
    receipt = inbox.lookup(batch.issuerNodeId, batch.namespaceId,
                            batch.issuerEpoch, batch.batchId)
    if receipt exists:
        if receipt.headerFingerprint is known and
           receipt.headerFingerprint != fingerprint(batch.header):
            reject BATCH_TRANSACTION_FAILED
        // ACK uses the durable receipt, never replay-supplied cursor/author.
        send ACK(batch.batchId, receipt.cursorEnd, 0, receipt.durableAuthor)
        return
    
    // ШАГ 2: Проверка курсора
    expected = peerState[batch.issuerNodeId, batch.namespaceId].lastReceivedSeq + 1
    if batch.cursorStart != expected:
        send ERROR(SEQ_GAP)
        return
    
    // ШАГ 3: Проверка криптографической цепочки
    chain = (batch.issuerNodeId, batch.namespaceId, batch.issuerEpoch)
    if not verifyBatchChain(chain, batch.prevBatchDigest, batch.batchDigest):
        send ERROR(BATCH_CHAIN_BROKEN)
        return
    
    // ШАГ 4: Атомарное применение
    begin transaction
    try:
        records = decodeRecordsArray(batch.records)
        for each mutation in records.mutations:
            for each fieldOp in mutation.fieldOps:
                authorNodeId = resolveAuthor(fieldOp)
                result = applyFieldWrite(mutation.recordId, fieldOp.fieldId, fieldOp)
                if result.changed:
                    updateBucketDigest(...)
        
        inbox.add(batch.issuerNodeId, batch.namespaceId, 
                  batch.issuerEpoch, batch.batchId)
        peerState[...].lastReceivedSeq = batch.cursorEnd
        lastBatchDigest[chain] = batch.batchDigest
        commit
        send ACK(batch.batchId, batch.cursorEnd, appliedCount, 0)
    catch error:
        rollback
        send ERROR(error.code, batch.batchId)
```

**Обоснование:** Если узел B применил батч и продвинул `lastBatchDigest`, но ACK потерялся, узел A повторно шлёт тот же батч. Без проверки идемпотентности первой узел B ошибочно отвергнет легитимный повтор из-за несовпадения `prevBatchDigest`.

**Инвариант [S7]:** При повторной доставке батча проверка идемпотентности выполняется **ДО** проверки `prevBatchDigest`. Это гарантирует корректную обработку потерянных ACK.

## 13.5. Мульти-пространственная синхронизация

Каждый `namespace` синхронизируется независимо. Координация между пространствами — ответственность приложения.

## 13.6. Ретрансляция: раздельные батчи и трансляция псевдонимов

### 13.6.1. Запрет коалесцирования

Ретранслятор **не коалесцирует** изменения от разных авторов в один батч. Каждый автор — отдельный батч.

### 13.6.2. Трансляция `origin` при ретрансляции

**КРИТИЧНО:** При подготовке кадра для целевого пира ретранслятор **обязан** транслировать `origin` каждой операции в псевдоним автора, согласованный в текущей сессии с получателем.

```
createDeltaBatchPacket(targetPeerId, filterAuthorNodeId):
    packet = DELTA_BATCH {
        issuerNodeId = self.nodeId,
        issuerEpoch = self.epoch,
        records = []
    }
    
    for each outboxEntry in outbox.filter(authorNodeId == filterAuthorNodeId):
        // Трансляция псевдонима в пространство получателя
        targetOrigin = aliasMap[targetPeerId].getAlias(filterAuthorNodeId)
        if targetOrigin is None:
            reject the entire batch with UNKNOWN_ALIAS  // never skip and create a stream hole
        
        fieldOp = outboxEntry.payload.copy()
        fieldOp.origin = targetOrigin  // ПЕРЕЗАПИСЬ псевдонима
        
        packet.records.append(fieldOp)
    
    return packet
```

**Обоснование:** Если ретранслятор просто скопирует байты от отправителя, получатель декодирует `origin` в чужом пространстве нумерации сессии, что приведёт к `UNKNOWN_ALIAS` или неверной идентификации автора.

**Инвариант [R4]:** При ретрансляции узел обязан транслировать `origin` каждой операции в псевдоним автора, согласованный в текущей сессии с получателем. Разрешение конфликтов всегда опирается на постоянный `authorNodeId` (16 байт).

# 14. E2EE / Zero-Knowledge Sync

## 14.1–14.4. Принцип и видимость

Сервер видит `fieldId`, `keyEpoch`, `hlc`, `authorNodeId`, `value` (шифротекст). Не видит содержимое.

## 14.5. Шифрование

```
nonce = KDF-SHA256(
    namespaceKey, "BIN-SYNC/E2EE/nonce/v1",
    recordId || fieldId || hlc.wall || hlc.logical || authorNodeId || keyEpoch
)[0..11]

value = ChaCha20-Poly1305(key, nonce, plaintext)
```

**Инвариант [E1]:** Одноразовый номер уникален для каждой комбинации `(запись, поле, время, автор, эпоха ключа)`.

## 14.6. Слепое слияние

Сервер применяет слияние по открытым `hlc` и `authorNodeId`, не расшифровывая `value`.

## 14.7. Матрица поддержки

- `LWW_RECORD`, `LWW_FIELD`, `BLOB_REF`, `SET_OR`: слепое слияние на сервере.
- `COUNTER_G`, `COUNTER_PN`, `SEQ_CRDT`: **Append-Only Envelope Store** (только на клиентах).
- `MANUAL`: сервер не детектирует конфликты.

## 14.8. Подписи

`Ed25519` подпись над полезной нагрузкой подписи батча.

## 14.9. Ротация ключей

Кадр `KEY_ROTATION` с доказательством эпохи. Клиент при отсутствии ключа сохраняет запись как нерасшифровываемую.

# 15. Безопасность

## 15.1–15.5. Транспорт, аутентификация, авторизация

Обязательный шифрованный транспорт. Списки контроля доступа на уровне пространства имён. Зажим перекоса для всех пиров.

## 15.6. Модель доверия (три типа)

- **При первом использовании (TOFU):** первый ключ запоминается навсегда.
- **Заранее согласованные ключи:** список разрешённых ключей.
- **Центр сертификации:** сертификат в аутентификационной нагрузке.

## 15.7. Защита от атак

Декомпрессионные бомбы, отравление временем, повторная передача, посредник, подмена авторства.

# 16. Контрактные инварианты

## 16.1. Инварианты слияния

```
[С1] Коммутативность: слить(А, Б) == слить(Б, А)
[С2] Идемпотентность: слить(А, А) == А
[С3] Ассоциативность: слить(А, слить(Б, В)) == слить(слить(А, Б), В)
[С4] Монотонность: после слияния состояние каждого поля не меньше, чем до слияния
```

## 16.2. Победа удаления

```
[У1] Томбстоун с временем Т подавляет запись поля с временем не больше Т
[У2] Запись поля с временем больше Т остаётся призраком
[У3] Обычная запись поля не меняет жизненный цикл
[У4] Мёртвый жизненный цикл и все поля томбстоуны/призраки — сущность удалена
[У5] Пустой документ не равен удалённой сущности
[У6] Узел не может применить дельту, если томбстоун был удалён сборщиком мусора
[У7] Призрачный статус вычисляется по автору поля против автора жизненного цикла, не по псевдониму
```

## 16.3. Независимость от идентичности

```
[И1] Слияние не зависит от сессионного псевдонима
[И2] Разрешение конфликтов: больший автор выигрывает
[И3] Псевдоним без резолва — отклонение
[И4] Автор всегда сохраняется локально (независимо от формата передачи)
[И5] При ретрансляции разрешение конфликтов по автору оригинала
[И6] Крышка идентифицируется (автор, последовательность), псевдоним в крышку не входит
```

## 16.4. Консистентность дайджестов

```
[Д1] Одинаковые состояния дают одинаковые дайджесты записи
[Д2] Разные версии дают разные дайджесты записи
[Д3] Сумма, исключающее или, количество корзины — вероятностная сводка; криптографическая целостность обеспечивается дайджестом записи / корневым дайджестом состояния
[Д4] Расхождение корзин влечёт расхождение дайджеста состояния
[Д5] Шифрование: одинаковый шифротекст даёт идентичные дайджесты
[Д6] Дайджест вычисляется по автору (16 байт), никогда по псевдониму (2 байта)
[Д7] Одинаковые (стенка, логика, автор, значение) дают идентичную полезную нагрузку дайджеста поля
[Д8] Автор жизненного цикла всегда входит в дайджест как 16-байтовый идентификатор
```

## 16.5. Инварианты последовательности

```
[П1] Последовательность монотонна на (автор, пространство имён) и не переиспользуется
[П2] Начало курсора батча равно последнему полученному номеру плюс один
[П3] Курсор атомарно скачет на конец курсора после применения батча
[П4] Повторный батч с тем же идентификатором — бездействие, но подтверждение обязательно
[П5] Последовательность исходящего журнала не переиспользуется после сбоя
[П6] Последовательность является курсором (автор, пространство имён), а не идентификатором пира
[П7] Идемпотентность проверяется до проверки дайджеста предыдущего батча
```

## 16.6. Безопасность сборки мусора

```
[СМ1] Безопасная последовательность — минимум подтверждённых номеров активных членов
[СМ2] Новый член не входит в минимум до снапшота
[СМ3] Томбстоун нельзя удалить, пока его время не ниже безопасной последовательности всех видевших
[СМ4] Ушедший член исключается из минимума
[СМ5] Автора счётчика можно удалить только если его максимум влит во всех активных
[СМ6] Запись входящего журнала удаляется после подтверждения обеими сторонами
[СМ7] Минимальный срок хранения томбстоунов не меньше удвоенного времени распространения членства
```

## 16.7. Стабильность схемы

```
[СХ1] Неизвестное пространство имён — отклонение или карантин
[СХ2] Неизвестный идентификатор поля — сохранить как сырой тег-длина-значение, в дайджест
[СХ3] Идентификатор поля не переиспользуется
[СХ4] Смена типа — новый идентификатор поля
[СХ5] Смена политики слияния — инкремент версии схемы
[СХ6] Длина значения и тип поля согласованы
[СХ7] Ожидающая схема не продвигает последний полученный номер
```

## 16.8. Канон

[К1] Два энкодера — байт-в-байт одинаковый результат
[К2] Избыточное переменное целое — отклонение
[К3] Не-число — отклонение
[К4] Минус ноль нормализуется в плюс ноль
[К5] Все массивы предваряются количеством

## 16.19. Каузальные зависимости (экспериментально)

```
[КЗ1] Таймаут зависимости — отбрасывание записи
[КЗ2] Цикл в графе зависимостей — отбрасывание записи
[КЗ3] Потерянная зависимость — отбрасывание записи, включая транзитивных потомков
[КЗ4] Ожидающая запись не продвигает курсор
[КЗ5] Батч с ожидающими записями не применяется частично
```

**Опциональный causal trailer DELTA_BATCH:**
- Включается только при установленном `Batch.Flags & 0x20`; стандартный payload без флага не содержит trailer.
- Формат: `magic u32 LE (0x31444343) | entryCount varint | (changeId b128 | depCount varint | sorted unique dep b128*)* | trailerLength u32 LE`. Последнее поле — длина от magic до последней зависимости, не включая само поле длины.
- Позиция trailer вычисляется только по footer length; поиск magic внутри payload запрещён. `entryCount` должен совпадать с числом записей тела, а trailer `changeId` — с соответствующим ChangeId записи.
- Зависимости строго возрастают в unsigned-лексикографическом порядке b128, нулевые и повторные ID запрещены. На один entry допускается не более 4 096 deps, на trailer суммарно — не более 250 000 deps; число entries — не более 100 000.
- Декодер сначала полностью проверяет trailer и только затем публикует CausalDeps; частичное изменение записей при ошибке запрещено. При установленном флаге отсутствующий/повреждённый trailer — ошибка всего payload.
- Внутрибатчевые зависимости разрешены только на более ранние записи того же батча и считаются удовлетворёнными атомарным применением; forward reference и дубли ChangeId запрещены.
- Состояние CausalTracker (known/lost/pending) находится в памяти процесса и не входит в Node WAL/snapshot; приложение обязано восстановить его после перезапуска через NoteCausalApplied/MarkLost.
- Duplicate DELTA_BATCH распознаётся по durable Inbox key до causal gate; повторная доставка ACK-ается независимо от trailer dependencies. Duplicate payload не является источником для восстановления known ChangeId: приложение восстанавливает tracker из собственного durable state.
- Causal trailer не входит в RecordsRoot/BatchDigest; его допустимо использовать только поверх канала с проверкой целостности/аутентификацией.
- Потерянный, просроченный или циклически отброшенный ChangeId становится недоступным для зависимых операций; все ожидающие транзитивные потомки также отбрасываются как LostDep. Повторное применение потерянного ID запрещено.

# 17. Лабораторные сценарии

## Сценарий 1. Полевой параллелизм
Два узла независимо изменяют разные поля. После синхронизации оба поля сохранены. Инварианты С1–С4.

## Сценарий 2. Удаление против поздней записи (победа удаления)
Один узел удаляет запись, другой в офлайне изменяет поле. Запись удалена, поле — призрак. У1–У5.

## Сценарий 3. Переподключение с новой картой псевдонимов
Слияние идентично при стабильных псевдонимах. И1–И3.

## Сценарий 4. Снапшот плюс хвост для нового пира
Новый пир получает снапшот на курсоре и хвост дельт. СН1, СН2.

## Сценарий 5. Счётчик с ушедшим узлом
Ушедший узел исключён из активных авторов. СМ5.

## Сценарий 6. Перекос часов
Отклонение с ошибкой перекоса часов.

## Сценарий 7. Регрессия эпохи
Отклонение с ошибкой регрессии эпохи.

## Сценарий 8. Канонический дайджест
Два энкодера — байт-в-байт одинаковый результат. К1.

## Сценарий 9. Инкрементальность дайджеста корзины
Вставка записей в любом порядке — идентичные количество, исключающее или, сумма. Д3.

## Сценарий 10. Предотвращение воскресения томбстоуна
Томбстоун не удалён сборщиком мусора до возврата узла. СМ3.

## Сценарий 11. Слепое слияние шифрования
Сервер применяет слияние по времени, не видя открытых данных. Ш1.

## Сценарий 12. Фрагментация
Большой чанк разбивается на фрагменты, собирается по идентификатору сообщения. Ц5–Ц7.

## Сценарий 13. Карантин зомби-узла
Отставший узел получает ошибку устаревшей ватермарки и полный ресинк.

## Сценарий 14. Защита от декомпрессионной бомбы
Отклонение до вызова декомпрессора.

## Сценарий 15. Обратное давление управления потоком
Отклонение при превышении кредитного окна. УП1, УП2.

## Сценарий 16. Ротация ключей
Повторное шифрование после получения нового ключа.

## Сценарий 17. Диапазонный курсор (коалесцирование)
Последний полученный номер равен концу диапазона. П2, П3, Т2.

## Сценарий 18. Потерянное подтверждение
Повторный батч — бездействие плюс повторное подтверждение. П4, П7.

## Сценарий 19. Ручной конфликт и разрешение поля
Разрешение через поле двести пятьдесят пять. РП1.

## Сценарий 20. Изоляция мульти-пространств
Одно пространство закрыто, другое работает.

## Сценарий 21. Свёртка корзин
Динамическая свёртка до минимального общего уровня. Д10.

## Сценарий 22. Доверие при первом использовании
Попытка подмены ключа — ошибка отозванного доверия. Д1.

## Сценарий 23. Разрешение конфликтов при ретрансляции (сохранение авторства)
Побеждает больший автор оригинала, не ретранслятор. И4, И5, А1–А5.

## Сценарий 24. Защита от неизвестного псевдонима [А3, Т1]

**Инварианты:** А3 (Неизвестный псевдоним — отказ всего батча), Т1 (Атомарность транзакции батча / откат).

**Описание:** Злоумышленник или рассинхронизированный узел передаёт батч с дельтой, где в поле псевдонима указано значение 9999, отсутствующее в локальной таблице псевдонимов принимающего узла.

**Предусловия:** Узел А соединён с узлом Б. Таблица псевдонимов узла Б содержит только легитимные псевдонимы текущей сессии.

**Шаги:**
1. Узел А формирует кадр батча дельт, содержащий операцию с псевдонимом 9999.
2. Узел Б выполняет валидацию батча при парсинге записей.

**Критерий успешности:**
- Приёмник отвергает батч с кодом ошибки «Неизвестный псевдоним».
- Ни одна операция из этого батча не попадает в хранилище (атомарный откат).

## Сценарий 25. Конкурентное удаление — разрешение по автору жизненного цикла [Ж1–Ж4, У7]

**Инварианты:** Ж1–Ж4 (Детерминизм жизненного цикла), У7 (Разрешение конфликтов удаления по автору), Д1 (Идентичный дайджест состояния).

**Описание:** Два узла одновременно удаляют одну и ту же запись с абсолютно идентичным физическим и логическим временем (стенка=500000, логика=0). Конфликт разрешается детерминированно по глобальному шестнадцатибайтному автору (автор узла Б больше автора узла А).

**Предусловия:** Узлы А (автор-А) и Б (автор-Б) имеют общую запись.

**Шаги:**
1. Узел А локально выполняет удаление записи с временем (500000, 0, псевдоним_А).
2. Узел Б локально выполняет удаление записи с временем (500000, 0, псевдоним_Б).
3. Узлы выполняют взаимный обмен дельтами.

**Критерий успешности:**
- На обоих узлах запись помечена как удалённая.
- Поле автора жизненного цикла на обоих узлах детерминированно равно автору узла Б.
- Дайджесты записей на А и Б побайтово совпадают.

## Сценарий 26. Восстановление после повреждённого кадра (контрольная сумма) [Ц1–Ц4]

**Инварианты:** Ц1–Ц4 (Контрольные суммы кадра), код ошибки «Повреждённый кадр», сохранение транзакционной чистоты хранилища.

**Описание:** В процессе передачи полезная нагрузка кадра повреждается (инверсия бита). Получатель обнаруживает несовпадение контрольной суммы, отбрасывает повреждённый кадр без изменения локального хранилища. При последующей повторной передаче неповреждённого кадра данные успешно применяются.

**Предусловия:** Узел А генерирует валидный пакет батча дельт для узла Б.

**Шаги:**
1. В сформированном бинарном пакете инвертируется байт полезной нагрузки.
2. Пакет передаётся узлу Б.
3. Узел А повторно отправляет оригинальный валидный пакет.

**Критерий успешности:**
- Первый пакет отклонён с ошибкой «Повреждённый кадр».
- До повторной отправки запись отсутствует в хранилище Б.
- Второй пакет успешно принят, запись появляется в хранилище Б.

## Сценарий 27. Консистентность дайджестов через ретрансляцию [Д6–Д8, И1–И5]

**Инварианты:** Д6–Д8 (Канонический дайджест с шестнадцатибайтным автором), И1–И5 (Сохранение канонического авторства при ретрансляции).

**Описание:** Узел А создаёт запись с автором А. Узел Б ретранслирует операцию узлу В. На узле В канонический дайджест записи и корзины вычисляется по оригинальному автору А, а не по промежуточному ретранслятору Б.

**Предусловия:** Топология цепочки А → Б → В. В каждой сессии согласованы свои сессионные псевдонимы.

**Шаги:**
1. Узел А записывает поле и передаёт дельту узлу Б.
2. Узел Б принимает дельту, переупаковывает её с адаптацией сессионного псевдонима и передаёт узлу В.
3. Вычисляются контрольные дайджесты на узлах А, Б и В.

**Критерий успешности:**
- Дайджест А равен дайджесту Б равен дайджесту В с абсолютной побайтовой идентичностью.

## Сценарий 28. Ретрансляция с раздельными батчами по авторам [Р1–Р3]

**Инварианты:** Р1–Р3 (Сепарация дельт по авторам), изолированное формирование батчей.

**Описание:** Ретранслятор Б накапливает дельты от независимых узлов А и Х. При взаимодействии с узлом В ретранслятор формирует батч с фильтром по автору А.

**Предусловия:** В исходящем журнале узла Б присутствуют дельты от нескольких авторов.

**Шаги:**
1. Узел Б генерирует пакет дельт с указанием фильтра по автору А.
2. Пакет доставляется узлу В.

**Критерий успешности:**
- Узел В получает и применяет только записи автора А.
- Записи автора Х в хранилище В отсутствуют.

## Сценарий 29. Привязка состояния снапшота и хвоста дельт [СН1–СН4]

**Инварианты:** СН1–СН4 (Контрольный дайджест снапшота), монотонный накат хвоста дельт.

**Описание:** Узел Б инициализируется через снапшот базы узла А (курсор Н). После применения снапшота узел А генерирует новые правки (курсоры Н+1 до М) и передаёт их как инкрементальный хвост дельт.

**Предусловия:** Узел А содержит записи 1–3. Узел Б пуст.

**Шаги:**
1. Узел А передаёт снапшот состояния на курсоре 3. Узел Б применяет его.
2. Узел А локально выполняет записи 4 и 5.
3. Узел А формирует пакет дельт с диапазоном [4, 5] и передаёт узлу Б.

**Критерий успешности:**
- Все 5 записей на узле Б идентичны записям узла А.
- Итоговые дайджесты записей совпадают.

## Сценарий 30. Целостность цепочки батчей [Т3]

**Инварианты:** Т3 (Криптографическая цепочка дайджестов предыдущих батчей), отказ при разрыве цепочки.

**Описание:** Проверка невозможности внедрения или подмены батча в середине потока репликации. Каждый последующий батч обязан содержать хеш предыдущего принятого батча.

**Шаги:**
1. Узел А передаёт узлу Б легитимный Батч 1 (дайджест предыдущего = 0). Батч успешно принят.
2. Злоумышленник пытается отправить узлу Б Батч 2 с поддельным дайджестом предыдущего батча.
3. Узел А отправляет легитимный Батч 2 с правильным дайджестом предыдущего батча.

**Критерий успешности:**
- Поддельный батч отклоняется с ошибкой «Транзакция батча не удалась».
- Легитимный Батч 2 успешно применяется.

## Сценарий 31. Аутентификационная нагрузка в приветствии [Д5]

**Инварианты:** Д5 (Аутентификация пира при рукопожатии), ошибка аутентификации.

**Описание:** При установлении сессии пиры валидируют аутентификационный токен или цифровую подпись. Защита от несанкционированного подключения к закрытому пространству репликации.

**Шаги:**
1. Неавторизованный узел пытается выполнить рукопожатие с некорректным токеном.
2. Авторизованный пир выполняет рукопожатие с валидным заранее согласованным токеном.

**Критерий успешности:**
- Попытка 1 завершается ошибкой аутентификации.
- Попытка 2 успешно открывает сессию репликации.

## Сценарий 32. Ожидающая схема [СХ7]

**Инварианты:** СХ7 (Карантин пакетов при опережающей версии схемы), атомарная разблокировка после обновления схемы.

**Описание:** Узел А отправляет батч, требующий версию схемы 2. Узел Б имеет зарегистрированную схему только версии 1. Приёмник не может корректно распарсить типы полей и переводит батч в состояние ожидания.

**Шаги:**
1. Узел Б получает батч с версией схемы 2 и возвращает ошибку «Схема в ожидании». Хранилище не изменяется.
2. Узел Б регистрирует новую спецификацию схемы версии 2.
3. Батч повторно передаётся узлу Б.

**Критерий успешности:**
- На шаге 1 возвращён код «Схема в ожидании».
- На шаге 3 батч успешно применён.

## Сценарий 33. Каузальные зависимости — таймаут [КЗ1]

**Инварианты:** КЗ1 (Карантин зависимых операций), ошибка таймаута каузальной зависимости.

**Описание:** Операция поступает с указанием родительской каузальной зависимости, которая отсутствует в локальном журнале. При превышении тайм-аута ожидания родителя операция переводится в статус ошибки.

**Шаги:**
1. Поступает зависимая операция, ожидающая несуществующую зависимость.
2. Истекает тайм-аут ожидания родительской транзакции.

**Критерий успешности:**
- Фиксируется отказ применения по таймауту.
- Неконсистентное состояние не проникает в основное дерево данных.

## Сценарий 34. Каузальные зависимости — обнаружение цикла [КЗ2]

**Инварианты:** КЗ2 (Ацикличность каузального графа), ошибка обнаружения цикла.

**Описание:** В результате аномалии распределённой сети или вредоносных действий две операции взаимно ссылаются друг на друга. Детектор циклов обязан прервать взаимную блокировку.

**Шаги:**
1. В очередь каузального анализатора подаётся граф с циклическими зависимостями.
2. Выполняется обход графа зависимостей.

**Критерий успешности:**
- Алгоритм детектирует цикл.
- Цикл разрывается детерминированным отбрасыванием одной из ветвей, взаимная блокировка исключена.

## Сценарий 35. Защита от зомби-реплик [У6, Д6, СМ7]

**Инварианты:** У6, Д6 (Карантинный горизонт надгробий), ошибка устаревшей ватермарки, принудительный ресинк через полный снапшот.

**Описание:** Узел выполнил сборку мусора надгробий до метки минимального времени надгробий. Зомби-реплика, спавшая дольше срока хранения надгробий, присылает правку с временем меньше метки. Принятие такой правки грозит воскрешением давно удалённых данных.

**Шаги:**
1. Узел фиксирует локальную ватермарку очистки.
2. Поступает дельта от зомби-узла с временем меньше ватермарки.

**Критерий успешности:**
- Дельта категорически отвергается с ошибкой устаревшей ватермарки.
- Узлу выставляется флаг обязательного обновления через полный снапшот.

## Сценарий 36. Разделение сети (расщепление мозга) и исцеление

**Инварианты:** С1 (Коммутативность), С3 (Ассоциативность), Д1 (Идентичные дайджесты при сходимости).

**Описание:** Кластер из трёх узлов {А, Б, В} разделяется на партиции {А, Б} и изолированный узел {В}. В обеих изолированных частях происходят параллельные конкурирующие изменения полей. После исцеления сети запускается многораундовый обмен дельтами.

**Шаги:**
1. В партиции {А, Б} узлы изменяют поля 0х0100 и 0х0101 и синхронизируются.
2. В изолированном узле {В} выполняется запись поля 0х0100 со старым временем и нового поля 0х0102.
3. Восстановление связности: узлы выполняют три раунда полного попарного обмена дельтами.

**Критерий успешности:**
- Конкурентное поле 0х0100 принимает значение из партиции {А, Б} по правилу победы последней записи.
- Поле 0х0102 успешно добавляется на все узлы.
- Дайджесты записей на всех трёх узлах совпадают.

## Сценарий 37. Кольцевая топология и остановка эха [Ш2]

**Инварианты:** С2 (Идемпотентность), П4 (Повторные дельты — бездействие), гарантия отсутствия лавинного шторма сообщений, Ш2 (Остановка эха).

**Описание:** Кольцо А → Б → В → А. Узел А инициирует изменение. Оно передаётся узлу Б, Б ретранслирует узлу В, а В ретранслирует обратно узлу А. Узел А распознаёт собственную правку, применяет её как бездействие (изменено = ложно) и не пересылает повторно.

**Шаги:**
1. Узел А создаёт запись. Размер исходящего журнала А равен одному.
2. А передаёт Б: узел Б применяет дельту и помещает её в исходящий журнал Б для В.
3. Б передаёт В: узел В применяет дельту и помещает её в исходящий журнал В для А.
4. В передаёт А: узел В отправляет дельту обратно узлу А (замыкание кольца).

**Критерий успешности:**
- Пакет успешно обработан на узле А.
- Размер исходящего журнала А остался строго равен одному (эхо остановлено, лавинное зацикливание предотвращено).

## Сценарий 38. Полный цикл жизненного цикла

**Инварианты:** У1 (Томбстоун подавляет меньшее время), У2 (Поля-призраки), У4 (Жизненный цикл ноль воскрешает поля-призраки), У5 (Итоговая победа удаления).

**Описание:** Комплексная проверка жизненного цикла записи: удаление → запоздалая запись в офлайне → перевод в призрак → воскрешение с восстановлением полей → финальное удаление.

**Шаги:**
1. Узел А удаляет запись с временем 500.
2. Узел Б в офлайне выполняет запись поля с меньшим временем 400.
3. Синхронизация А передаёт Б: на Б запись мертва, а поле помечено как призрак.
4. Узел А выполняет воскрешение записи с временем 600. Синхронизация А передаёт Б: запись оживает, поле теряет статус призрака.
5. Узел Б повторно удаляет запись с временем 700.

**Критерий успешности:**
- На всех этапах корректно переключаются флаги «мертва» и «призрак».
- В финале на обоих узлах запись окончательно удалена.

## Сценарий 39. Мульти-полевой атомарный батч [Т1]

**Инварианты:** Т1 (Атомарность пакета дельт), С4 (Полевой гранулярный победа последней записи).

**Описание:** Батч содержит обновления трёх полей одной записи. На принимающем узле одно поле уже было изменено локально более свежим временем. При приёме батча это поле сохраняет локальное значение, а остальные поля применяются.

**Шаги:**
1. Узел Б локально пишет первое поле с временем 3000.
2. Узел А отправляет батч с тремя полями с временем 2000.
3. Узел Б обрабатывает входящий батч.

**Критерий успешности:**
- Первое поле на Б сохранило локальное значение (локальная победа последней записи выиграла).
- Остальные поля обновились значениями из батча.

## Сценарий 40. Каноническое кодирование чисел переменной длины [К2]

**Инварианты:** К2 (Минимальная длина переменного целого), каноничность без избыточных нулей.

**Описание:** Проверка кодирования и декодирования граничных числовых значений переменной длины: 0, 1, 127 (один байт), 128, 16383 (два байта), 16384 (три байта), два в степени тридцать один минус один (пять байт).

**Шаги:**
1. Числа сериализуются через кодирование переменного целого.
2. Выполняется десериализация через декодирование переменного целого.

**Критерий успешности:**
- Декодированное значение строго совпадает с исходным.
- Количество прочитанных байт строго равно фактической длине закодированного буфера (отсутствуют хвостовые нули).

## Сценарий 41. Коммутативность дайджеста корзины при перестановках [Д3]

**Инварианты:** Д3 (Коммутативность хеша корзины), инвариантность к порядку вставки.

**Описание:** Набор из ста хешей записей добавляется в три независимых аккумулятора корзин в трёх совершенно разных порядках: прямой, обратный и перемешанный (чётные/нечётные).

**Шаги:**
1. Аккумулятор один: вставка хешей в прямом порядке.
2. Аккумулятор два: вставка в обратном порядке.
3. Аккумулятор три: вставка в псевдослучайном перемешанном порядке.

**Критерий успешности:**
- Количество всех трёх аккумуляторов равно ста.
- Исключающее или всех трёх аккумуляторов одинаково.
- Сумма всех трёх аккумуляторов одинакова.

## Сценарий 42. Стресс-тест / хаос-рандомизация трёх узлов [С1–С4, Д1–Д5]

**Инварианты:** С1–С4 (Всеобщая сходимость), Д1–Д5 (Идентичные хеши корзин при хаотической доставке).

**Описание:** Три реплики (альфа, бета, гамма) параллельно выполняют двадцать пять случайных чередующихся операций (добавление, модификация, удаление и воскрешение полей) над пятью общими записями. Затем запускается четыре раунда случайного ячеистого обмена дельтами.

**Шаги:**
1. Псевдослучайная генерация двадцати пяти операций с чередованием авторов и записей.
2. Четыре раунда полного ячеистого обмена дельтами между всеми парами узлов.
3. Сверка состояний всех пяти записей на всех трёх узлах.

**Критерий успешности:**
- Ни один узел не падает с ошибкой рассинхронизации.
- Состояние всех записей на узлах альфа, бета, гамма сходится байт-в-байт.
- Дайджесты записей на всех трёх узлах идентичны для каждой из пяти записей.

---

## Сценарий 44. Snapshot-tail после compaction не перенумеровывает общий Outbox

**Инварианты:** E-15 (ACK watermark), E-17 (peer-relative cursor), S2 (непрерывность author stream), П7 (детерминированный replay).

**Описание:** Peer A подтверждает локальные cursor 1 и 2. После этого общий Outbox компактизирует префикс. Новый peer B получает snapshot, а затем delta-tail, начинающийся с wire cursor 1, хотя локальный cursor этой записи равен 3.

**Шаги:**
1. A получает и подтверждает изменения author stream с локальными cursor 1 и 2.
2. Outbox удаляет подтверждённый префикс; следующий локальный cursor остаётся равным 3.
3. B присоединяется и получает snapshot состояния, включающего изменения 1 и 2.
4. Для B строится delta-tail: локальный cursor 3 отображается в wire cursor 1 с offset 2.
5. Для A одновременно строится следующий batch: он обязан сохранить wire cursor 3.
6. Проверяется, что построение и доставка batch B не меняет Outbox.Seq, batch-id mapping и ACK watermark A.
7. Offset сохраняется, узел перезапускается, и следующий cursor 4 отображается в wire cursor 2.

**Критерий успешности:**
- B получает cursor 1, A получает cursor 3 для одной и той же локальной записи.
- Общий Outbox.Seq остаётся равным 3 до и после построения обоих batch.
- ACK B=1 преобразуется в local ACK=3; ACK A=3 остаётся local ACK=3.
- После restart offset B=2 сохраняется; local cursor 4 становится wire cursor 2.
- Ни один peer не теряет запись и не получает повторно уже подтверждённый диапазон.

## Сценарий 43. Сквозное сохранение ChangeId в mesh и защита snapshot

**Инварианты:** И4 (неизменность авторства/provenance), E-8 (relay eligibility), E-13 (подавление кольцевого эха), T1 (атомарность применения).

**Описание:** Узлы A, B и C обмениваются одной логической записью по маршруту A→B→C→A. Одновременно C получает ту же запись напрямую от A, то есть один `changeId` приходит через два независимых канала.

**Шаги:**
1. A создаёт изменение и фиксирует исходный `changeId`.
2. A передаёт батч B; B ретранслирует его C; C ретранслирует его A.
3. A передаёт тот же исходный батч C по независимому маршруту.
4. Проверяются идентичность `changeId` на каждом relay-hop, отсутствие повторного enqueue и подавление возвратного эха.
5. Для snapshot проверяются отклонение нулевого/дублированного `changeId` и изменение `recordsRoot` при подмене идентификатора.

**Критерий успешности:**
- `changeId` совпадает с исходным на всех узлах и после каждого сетевого декодирования.
- Повторная доставка по второму маршруту не создаёт второй relay-entry.
- Возврат к исходному автору не создаёт эхо в Outbox.
- Snapshot с нулевым/дублированным ID или изменённым `changeId` при старом корне отвергается до изменения хранилища.

# 18. Эволюция схемы

## 18.1. Правила

Идентификатор поля не переиспользуется. Смена типа — новый идентификатор поля.

## 18.2. Изменение политики слияния

Требует инкремента версии схемы. Старые записи остаются со старой политикой.

## 18.3. Неизвестная схема

Ожидающая схема → запрос карты схем → применение после получения.

## 18.4. SCHEMA_MAP

Wire payload: `count: varint | descriptor*`, где каждый descriptor имеет layout:

`namespaceId: u16 LE | schemaId: u16 LE | version: u16 LE | mergePolicy: u8 | fieldCount: varint | fieldId: u16 LE* | retiredCount: varint | retiredFieldId: u16 LE*`.

- Ключ descriptor — `(namespaceId, schemaId, version)`; повторный ключ в одном SCHEMA_MAP запрещён.
- `fieldId` внутри descriptor строго возрастают и уникальны; `retiredFieldId` также строго возрастают и уникальны.
- Активные и retired field IDs не пересекаются.
- `descriptorCount` не превышает 100 000; суммарное количество active и retired field IDs в одной карте не превышает 250 000. Для одного descriptor совокупное число этих ID не превышает 65 536 (размер пространства u16).
- Каждый count проверяется до итерации/выделения памяти относительно оставшегося payload и установленных лимитов; после последнего descriptor обязателен EOF.
- При Learn дескриптор с недопустимыми диапазонами или пересечением active/retired отвергает входную карту до изменения registry. Повторная публикация уже известного ключа допустима только при полном совпадении mergePolicy, FieldIds и RetiredFieldIds. Конфликтующая версия не заменяет ранее зарегистрированную.

## 18.5–18.7. Совместимость

Неизвестные поля — сырой тег-длина-значение, в дайджест. Обратная и прямая совместимость.

    числовой идентификатор поля, осведомлённый о схеме

    не глобальный курсор

записи:
    абсолютная запись поля / томбстоун поля
    стабильный ChangeId (b128) проходит через всю цепочку relay и включён в RecordsRoot
    жизненный цикл (поле ноль) — победа удаления
    без патча относительно базы
    авторство сохраняется через цепочку псевдонимов или полный режим автора

слияние:
    подключаемые политики на пространство имён
    зернистость слияния = зернистость часов
    без сброса на уровне записи перед слиянием полей

    подавление кольцевого эха через проверку идентичности

дайджест:
    хэш дайджест записи (сто двадцать восемь или двести пятьдесят шесть бит)
    шифрование: дайджест по шифротексту
    полезная нагрузка дайджеста поля с шестнадцатибайтным автором (не псевдонимом!)
    полезная нагрузка дайджеста жизненного цикла с автором жизненного цикла
    корзина = количество + исключающее или + сумма (коммутативные)
    префикс = хэш(идентификатор записи)
    динамические биты ветвления корзин
    свёртка корзин для разной глубины
    разбиение диапазона внутри хэш-префикса

журнал:
    последовательность исходящего журнала на (автор, пространство имён)
    диапазонный курсор [начало..конец]
    входящий журнал (издатель, пространство имён, эпоха, идентификатор батча) идемпотентность
    упорядоченность на (узел пира, пространство имён)
    идемпотентность проверяется до проверки дайджеста предыдущего батча

сравнение:
    курсор → префиксные корзины → разбиение диапазона → инвертируемый фильтр → снапшот + хвост

снапшот:
    все живые + томбстоуны в окне сборки мусора + призраки
    сортировка по хэш(идентификатор записи)
    чанки по одному мегабайту, дайджест чанка + дайджест снапшота + дайджест состояния снапшота + контрольная точка
    возобновляемость с любого индекса чанка

    раздельные батчи по авторам
    трансляция псевдонима через карту псевдонимов получателя
    издатель = ретранслятор
    автор в полях = оригинальный автор

членство:
    ушёл > приостановлен > активен
    карантин зомби-узлов
    минимальный срок хранения томбстоунов не меньше удвоенного времени распространения членства

транспорт:
    транспортно-независимый
    кадр: двадцать пять байт заголовка, магия, контрольная сумма
    мультиплексирование потоков
    фрагментация логических сообщений
    обновление окна с аддитивными кредитами

безопасность:
    шифрованный транспорт обязательный
    подписи батчей для ячеистой сети
    шифрование: значение зашифровано, время открыто
    слепое слияние на недоверенных серверах
    хранилище конвертов для счётчиков и последовательностей в шифровании
    ротация ключей с эпохой
    формальная деривация одноразового номера
    модель доверия: при первом использовании / заранее согласованные / центр сертификации

транзакции:
    батч дельт как атомарная единица
    применение «всё или ничего»
    атомарный скачок курсора на конец курсора

инварианты:
    все группы инвариантов от слияния до каузальных зависимостей

# Приложение E. Сквозной пример сессии

**Топология:** А —(сессия один)— Сервер —(сессия два)— Б

1. **А создаёт запись:** идентификатор записи=0х1111..., поле 0х0100=0х42, время=(тысяча, ноль), автор=0хАААА...
2. **А передаёт Серверу: Приветствие** с идентификатором узла=0хАААА, модель доверия=при первом использовании.
3. **Сервер передаёт А: Подтверждение приветствия** плюс идентификатор сессии.
4. **А передаёт Серверу: Карта псевдонимов** (А=0х0001, Сервер=0х0002).
5. **А передаёт Серверу: Батч дельт** с псевдонимом=0х0001 (псевдоним А в сессии А↔Сервер).
6. **Сервер применяет:** резолвит псевдоним=0х0001 → автор=0хАААА.
7. **Сервер ретранслирует Б:** создаёт новый батч, **транслирует псевдоним** в псевдоним А в сессии Сервер↔Б (например, 0х0003). Автор в метаданных остаётся 0хАААА.
8. **Б применяет:** резолвит псевдоним=0х0003 → автор=0хАААА.
9. **Итог:** А, Сервер, Б имеют байт-идентичное состояние. Дайджесты идентичны (Д6).

Документ самодостаточен и описывает нормативный контракт BIN-SYNC CORE v2.4.20 FINAL. В версиях 2.3.6–2.4.0 последовательно закрыты критические проблемы, выявленные при практической реализации:

1. **Порядок проверок** в применении батча предотвращает ложные отказы при потерянных подтверждениях.
2. **Трансляция псевдонимов** гарантирует корректную идентификацию автора в ячеистых топологиях.

Сорок два лабораторных сценария покрывают все выявленные режимы отказов.

# ERRATA v2.3.7 (итог практической реализации, референс-код `binsync/`, 49/49 тестов зелёные)

Все пункты ниже выявлены при написании и прогоне эталонной реализации. Каждый пункт содержит: раздел спецификации, суть дефекта, нормативную правку. Реализация снабжена трассировочными комментариями `SPEC CORRECTION (errata E-n)` в местах правок.

## E-1. §4.3/§4.6 — модель авторства: durable author = bare nodeId (16 байт)
**Дефект:** первоначальная «закалка» привязки `(nodeId, epoch)` как составного идентификатора автора ломала сходимость анти-энтропии: локальные записи узла имели автора 16 байт, резолвленные через ALIAS_MAP — 20 байт, разные recordDigest на концах сессии (§17.1 не сходился).
**Нормативно:** подтверждается буква §4.6: автор — **durable b128 nodeId без эпохи**. Эпоха живёт только в привязках алиасов (§4.3) и в issuerEpoch батчей (§12.17). Tie-break §5.4 сравнивает 128-bit nodeId.

## E-2. §4.4/§12.17 — watermark'и эпох ключуются СЕССИЕЙ получателя, а не автором
**Дефект:** §4.4 («remote.epoch < known.epoch[nodeId]») при ретрансляции неоднозначен: реле не может штамовать чужие операции эпохой автора без нового wire-поля; глобальное сравнение по nodeId отвергало легитимные прямые батчи того же узла как EPOCH_REGRESSION (сценарий 42), а включение проверяемого issuerEpoch в ключ делало проверку тавтологией (сценарий 7 не срабатывал).
**Нормативно:** существуют два непересекающихся уровня watermark: (а) `PeerSessionEpochs[senderPeer]` — peer-wide incarnation baseline, полученный только из HELLO/ALIAS_MAP live-канала; (б) `KnownEpochs[(senderPeer, namespaceId)]` — namespace-specific watermark, повышаемый только после полного принятия батча. Эффективный watermark для приёма в namespace равен `max(PeerSessionEpochs[senderPeer], KnownEpochs[(senderPeer, namespaceId)])`, если оба значения существуют. Эти значения хранятся раздельно: `namespaceId = 0` — обычный namespace, а не sentinel. Durable author metadata (`namespace = -1`) также остаётся отдельной областью. Переподключение не снижает peer-wide baseline и не удаляет namespace-specific watermarks. Сравнение ведётся против эффективного watermark, никогда против собственного штампа батча.

## E-3. §10.4/STEP 2 — приёмный курсор ключуется (senderPeer, senderEpoch, ns)
**Дефект:** единый курсор на durable issuerNodeId смешивал стримы разных incarnations одного узла.
**Нормативно:** receive-cursor — per session stream `(senderPeer, senderEpoch, namespaceId)`; новый incarnation начинает с 0 ([S2]).

## E-4. §10.2.2/§13.6.1 [Р3]/ACK — push-watermark'и и ACK ключуются АВТОРСКИМ СТРИМОМ
**Дефект:** скалярный `lastAckedSeq` на пару (peer, ns) некорректен при одном отправителе с несколькими авторами в outbox (один батч = один автор по [Р3]): ACK за стрим X двигал курсор стрима Y → потеря операций или бесконечный повтор (KeyError-каскады сценариев 02/32/38/42).
**Нормативно:** (а) последовательность seq — per (authorStream, targetPeer, ns); (б) кадр ACK (§12.11) получает **необязательный trailer: b128 author stream**; при его отсутствии (совместимость/sneakernet) применяется консервативное правило: двигать только те стримы, чей первый не-ACK'нутый seq ≤ ackedSeq, никогда дальше головы стрима ([П2]); (в) replay-кэш детерминированного batchId (§10.2.2) ключуется (stream, cursorEnd).

## E-5. §4.3 — коллизии алиасов решаются fail-closed
**Дефект:** при конфликте привязок в таблице сессии реализация молча переиспользовала занятый номер → misattribution авторов.
**Нормативно:** [А3] уточняется: если для (nodeId, epoch) нет свободного номера без конфликта, отправка прерывается с UNKNOWN_ALIAS до полного re-handshake; частичная привязка в live-сессии запрещена. Инкрементальная propagation изученных привязок моделируется повторным ALIAS_MAP-кадром (§12.7) с двусторонним согласованием номера.

## E-6. §13.6.1 — выбор автора для дельта-батча
**Дефект:** эвристический выбор «первого автора по порядку outbox» голодал стримы, чья следующая запись стояла за gap'ом другого автора (операции никогда не покидали outbox — сценарий 42).
**Нормативно:** выбирается автор с минимальным не-подтверждённым seq среди стримов, пригодных к доставке данному пиру; gap'нутый стрим остаётся fallback'ом, но не блокирует остальные.

## E-7. §13.6.2 [R4]/[И4] — relay сохраняет payload ВЕРБАТИМ
**Дефект:** пересборка op с нейтральным origin=0 при ретрансляции теряла возможность обратного резолва автора (alias_of(0)=None → UNKNOWN_ALIAS или mis-stamped операция).
**Нормативно:** реле кладёт в свой outbox исходный wire-payload без переписывания; трансляция origin в alias целевой сессии выполняется исключительно в момент сборки батча для конкретного получателя ([R4]). createdAt relay-записи = wall-time самого op, не локальные часы реле (детерминизм дайджестов [Д1]).

## E-8. §8.3 [E2]/§17.23 — relay eligibility определяется PROVENANCE, а не исходом merge
**Дефект:** буквальное «queue if result.changed» оставляло проигравшую并发-операцию C навсегда на реле R (changed=False против победителя A; повторная доставка той же одно-записной операции короткозамыкалась STEP-1 идемпотентности по recordsRoot/batchId до всякого merge — сценарий 23).
**Нормативно:** право на ретрансляцию даёт **первое видение changeId**; истинные эхо подавляются множеством уже виденных changeId. Инварианты И4 (авторство сохраняется при ретрансляции) и требование mesh-сходимости §17.23 имеют приоритет над псевдокодом §13.4.

## E-9. §4.3 — durable-реестр авторов и сборка таблиц сессий
**Дефект:** re-handshake терял привязки третьих сторон, накопленные за время живой сессии → распад relay-цепочек (A→B→V→A).
**Нормативно:** каждый узел держит durable-реестр известных авторов; таблицы ALIAS_MAP новой сессии собираются как надстройка над реестром (старые привязки сохраняются, новые negotiate'ятся поверх).

## E-10. §12.7 — инкрементальные ALIAS_MAP обновления в live-сессиях
Формально кадр существует (§12.7), но порядок применения к уже открытым сессиям не был описан. Нормативно: изученная привязка транслируется во ВСЕ live-сессии, где она нужна для штамповки автора, включая зеркало в копию сессии со стороны отправителя (см. E-11). Коллизия → fail-closed (E-5).

## E-11. §4.3 — обе копии одной сессии обязаны иметь идентичные таблицы
**Дефект:** одностороннее обогащение карты приводило к UNKNOWN_ALIAS при re-stamping собственных операций отправителя.
**Нормативно:** [У уточнение]: любое изменение таблицы сессии на одной стороне влечёт симметричное применение на другой (протокол согласования номера — E-10).

## E-12. §12.17.2 — цепочка prevBatchDigest ключуется (issuer, ns, epoch) + targetPeer
**Дефект:** единая глобальная цепь на автора невозможна при [Р3] (получатель видит только свой стрим) → ложные BATCH_CHAIN_BROKEN.
**Нормативно:** batchId/prev/digest вычисляются per-stream ((issuer,ns,epoch), targetPeer) в момент отправки; чекпоинт цепиReceiver'а двигается только после ACCEPT; детерминированный replay потерянного батча воспроизводит тот же (batchId, prev) из кэша (E-4в).

## E-13. §8.3 [E2]/§17.37 — подавление кольцевого эха лавины (avalanche stop)
**Дефект:** даже при корректном provenance-гейте (E-8) автор узел A повторно ставил в outbox собственное состояние, возвращённое по кольцу A→B→V→A через ЧУЖОЙ канал (senderPeer=V): множество «виденных» changeId каналоспецифично, и эхо выглядело новой provenance → неограниченный рост outbox (нарушение [Ш2], ожидаемый размер ровно 1).
**Нормативно:** право на ретрансляцию дополнительно отсекается по **durable-состоянию**: если поле (recordId, fieldId) уже представлено в НЕПОДТВЁЖДЕННОМ outbox данного узла победителем с байт-идентичным (tag, hlc, value), а резолвленный автор совпадает с самим узлом — запись является эхом собственного состояния и НЕ ставится в очередь. Подавление локальной записи (§10.1) симметрично: write, восстановивший уже разосланное собственное состояние, не создаёт новую outbox-запись. Множество виденных changeId ключуется каналом provenance (senderPeer, ns, changeId), что сохраняет независимость sneakernet- и network-доставок одного и того же батча (§3.5).


## Прочие подтверждения и ужесточения
- **§6.1 [К2]:** varint каноничен ⇔ минимален ПО БАЙТАМ: декодер отвергает любой код с ведущими continuation-нулями (`0x80…` padding) и коды шире окна терминального байта (для nbytes>1 окно терминала = 7·(nbytes−1)+6 бит). Контрольный вектор CRC32C зафиксирован в тестах.
- **§12.x ERROR:** неизвестный алиас при получении — UNKNOWN_ALIAS (fail-closed), «тихий skip» запрещён (сохранение И4).
- **§7.4:** ghost-поля DEAD-записи сохраняются в состоянии (видимость по lifecycle HLC), undelete-операция propagates даже при changed=False локально (idempotent LWW + обязательность доставки перехода состояния [П7]).
- **§12.x кадры:** заголовок кадра упакован БЕЗ выравнивания (25 байт, little-endian packed); контрольная сумма покрывает все поля заголовка (реализационный дефект struct-выравнивания зафиксирован тестом).

# ERRATA v2.3.8

## E-14. §12.17 / §12.24 / §13.4 — ChangeId обязателен в канонической wire-записи

**Дефект:** `changeId` существовал в `OutboxEntry`, но не передавался в массиве `records`. При декодировании он становился нулевым, а принимающая сторона синтезировала новый случайный идентификатор. Это разрушало provenance при каждом relay-hop и делало дедупликацию mesh недостоверной.

**Нормативно:** каждая запись wire-массива имеет порядок `recordId b128 | changeId b128 | opKind u8 | payloadLen varint | payload`. `changeId` — обязательный ненулевой 128-битный идентификатор исходного изменения; ретранслятор сохраняет его побайтно. `recordsRoot` считается по полному каноническому массиву и тем самым связывает `changeId` с `batchDigest` и подписью. Нулевые и повторяющиеся в одном батче идентификаторы отвергаются до commit; то же правило применяется к snapshot batches. Старый wire-layout без `changeId` несовместим с v2.3.8 и не поддерживается этой версией протокола.

# ERRATA v2.4.0

## E-15. §10.4 / §12.23 — ACK не может продвигать watermark за отправленный stream

**Дефект:** полученный ackedSeq без проверки повышал StreamAcked, что позволяло некорректному ACK преждевременно очистить Outbox.

**Нормативно:** отправитель фиксирует максимальный cursor, реально переданный каждому peer отдельно по author stream. ACK с author stream принимается только если его cursor не выше зафиксированного pushed cursor и покрывает непрерывный диапазон записей Outbox. Legacy ACK без author ограничивается общим максимальным pushed cursor и продвигает каждый stream только по непрерывному диапазону. TCP ACK дополнительно обязан точно совпадать с BatchId, CursorEnd и DurableAuthor отправленного батча. Некорректный ACK отклоняется с ACK_OUT_OF_RANGE (0x0018) без изменения watermark и Outbox.

**Persistence:** per-peer/per-author StreamPushed сохраняется вместе с StreamAcked; формат node-state повышен до версии 3 (BIN-SYNC/NODESTATE/v3). Файлы state v1/v2 отвергаются как несовместимые, а не интерпретируются частично.

## E-16. §10.2.2 / §12.11 — author stream дубликата ACK привязан к BatchId

**Дефект:** LastStreamAuthor хранит только последнего автора, принятого от peer в namespace. Если peer передавал несколько author streams, повтор старого batch после более нового мог получить ACK с чужим автором.

**Нормативно:** при первом принятии узел сохраняет единый InboxReceipt для ключа (issuer, namespace, epoch, batchId): durable author, original cursorEnd, headerFingerprint, appliedAt и expiresAt. При duplicate replay ACK строится по сохранённым cursorEnd/author, а не по replay header или LastStreamAuthor. Fingerprint проверяет committed header, но намеренно не декодирует повторный payload и causal trailer. Node-state v8 сохраняет receipt атомарно; legacy v3-v7 receipts мигрируют с explicit unknown cursor/fingerprint markers.

## E-17. §10.5 / §12.17.2 — sequence Outbox неизменяема; cursor offset принадлежит peer

**Дефект:** нормализация разрыва после compaction изменяла `OutboxEntry.Seq` непосредственно при построении DELTA_BATCH для одного получателя. Outbox общий для всех peers, тогда как ACK-watermark индивидуален. Поэтому нормализация для нового peer могла перенумеровать запись ниже watermark старого peer; старый peer переставал видеть ещё не подтверждённое изменение.

**Нормативно:**
1. `OutboxEntry.Seq` — неизменяемый локальный durable cursor в пределах author stream. Построение батча не изменяет запись Outbox.
2. Для каждой пары (peer, namespace, author stream) хранится `StreamOffset >= 0`: `localCursor = wireCursor + StreamOffset`.
3. Если новый peer начинает delta-tail после уже скомпактированного префикса, его первый доступный local cursor `L` отображается в wire cursor 1; начальный offset равен `L - 1`. Это отображение действует только для данного peer и author stream.
4. `CreateDeltaBatch` формирует peer-relative sequence в лёгких копиях записей; payload и ChangeId остаются неизменными. Диапазон batch cursor и batch-id cache используют wire cursor.
5. ACK сначала проверяется по StreamPushed в wire coordinate, затем contiguous-range validation выполняется в local coordinate через offset. StreamAcked хранится в wire coordinate.
6. Compaction сравнивает local Outbox.Seq с `StreamAcked + StreamOffset` каждого заинтересованного peer. Отсутствие PeerState означает отсутствие ACK и не разрешает удаление.
7. Offset сохраняется вместе с PeerState. Node-state v4 ввёл сохранение StreamOffsets; node-state v5 (`BIN-SYNC/NODESTATE/v5`) дополнительно сохраняет peer-wide HELLO epochs отдельно от namespace watermarks. Reader поддерживает v3/v4: legacy `(peer, 0)` сохраняется как namespace-0 watermark и одновременно переносится в peer-wide baseline, чтобы не ослабить ранее действовавшую защиту от rollback. v1/v2 не поддерживаются.

**Инвариант:** изменение cursor mapping одного peer не может изменить cursor, batch-id, ACK или видимость записей для любого другого peer.


# ERRATA v2.4.4

## E-18. §13.1 — двустороннее подтверждение baseline и атомарный STATE_DIGEST

**Дефект:** после одного направления AutoReconcile принимающая сторона могла выставить `InitialSyncComplete`, хотя обратная передача snapshot ещё не завершилась. При разрыве между раундами это разрешало инициализацию peer-relative `StreamOffset` до подтверждения baseline в обоих направлениях.

**Нормативно:**
1. `InitialSyncComplete` устанавливается только после успешного завершения обоих направлений reconciliation в рамках одной операции AutoReconcile. Получатель snapshot подтверждает его применение завершающим пустым `NEED_RANGE`; отправитель считает свою сторону подтверждённой только после получения этого terminator.
2. Завершение только одного направления, ошибка передачи, отмена или разрыв соединения до завершения второго направления не устанавливают `InitialSyncComplete`. Повторное подключение должно продолжить reconciliation; уже применённые snapshot chunks безопасно объединяются по LWW.
3. Если количество расходящихся prefix достигло `maxPrefixes`, раунд считается ограниченным и не подтверждает полный baseline. Узлы повторяют AutoReconcile до раунда, в котором число divergent prefixes строго меньше лимита. Это консервативно трактует точное совпадение с лимитом как потенциально усечённый результат.
4. `STATE_DIGEST` строится под упорядоченными node gates: bucket digest и Outbox high-water cursor должны соответствовать одному атомарному view. Снимок, используемый для digest, не должен перечислять изменяемые Storage/Outbox коллекции без синхронизации.

**Wire format:** без изменений. Изменение уточняет локальную commit-семантику baseline и согласованность вычисления digest.


# ERRATA v2.4.5

## E-19. §12.6 / §13.1 — ограничение ресурсов при разборе SNAPSHOT_CHUNK

**Дефект:** недоверенный `ChunkCount` напрямую использовался как capacity для списка чанков. Значение до `uint.MaxValue` могло вызвать чрезмерное выделение памяти ещё до проверки целостности snapshot. Счётчики records/fields также приводились из varint к `int` без предварительной проверки, а остаточные байты payload игнорировались.

**Нормативно:**
1. Получатель отклоняет `ChunkCount = 0`, `ChunkIndex >= ChunkCount` и `ChunkCount > 4096` до выделения коллекций.
2. Один chunk содержит не более 100 000 records и 250 000 fields. Счётчики проверяются как `ulong` до преобразования к `int`.
3. Длина каждого field value должна быть не больше оставшегося payload и `Int32.MaxValue`.
4. После декодирования chunk reader обязан находиться в EOF; trailing bytes запрещены.
5. Отправитель формирует chunks, соблюдая те же лимиты records/fields, абсолютный `MAX_PAYLOAD_SIZE` и `ChunkCount <= 4096`; если отдельная запись не помещается в один frame, отправка завершается `PAYLOAD_TOO_LARGE` до начала передачи.
6. Те же ограничения chunk count применяются к прямому атомарному `ApplySnapshotChunks`.

**Wire format:** без изменений. Ограничения являются parser/resource bounds и не меняют кодирование корректных snapshot chunks в пределах установленных лимитов.


# ERRATA v2.4.6

## E-20. §9.1.4 / §12.7 / §13.1 — Outbox cursor не является частью STATE_ROOT

**Дефект:** Outbox sequence монотонен отдельно для каждого `(authorNodeId, namespaceId)`. Сведение независимых потоков к одному `max(seq)` создаёт неоднозначный scalar cursor: оно теряет идентичность author stream, может совпадать при разных наборах stream counters и различаться у узлов с идентичным реплицированным состоянием. Включение этого значения в `StateRootDigest` порождает ложное расхождение root digest, не соответствующее расхождению данных.

**Нормативно:**
1. `STATE_ROOT` хеширует только реплицируемое состояние namespace: `domainTag("BIN-SYNC/STATE/v2") || namespaceId || recordCount || sort_by_prefix_then_recordId(all BucketDigest canonical encodings)`. Outbox sequence counters, ACK watermarks, `StreamPushed` и `StreamOffsets` не входят в `STATE_ROOT`.
2. `OutboxEntry.Seq` и high-water counters остаются независимыми для каждого author stream. Их синхронизация и подтверждение выполняются только в соответствующем `(peer, namespace, authorNodeId)` контексте; агрегированный namespace-wide cursor запрещён.
3. Для сохранения layout существующего `STATE_DIGEST` поле `OutboxCursor : u64` остаётся на прежнем wire offset как зарезервированное поле. Отправитель обязан передавать `0`; получатель потребляет поле, но не использует его для сравнения состояния. Новые реализации нормализуют decoded `OutboxCursor` к `0`.
4. Совпадение `RootDigest` не заменяет проверку полученных bucket rows: divergent prefixes вычисляются по фактическому сравнению bucket entries. Root digest не считается аутентифицированным только на основании значения, присланного peer.
5. Смена domain tag с `BIN-SYNC/STATE/v1` на `BIN-SYNC/STATE/v2` отражает новую формулу root. При несовпадении root реализации продолжают сравнение bucket entries; несовпадение одного root без bucket divergence не требует snapshot.

**Wire layout:** размер и порядок полей `STATE_DIGEST` не меняются. Legacy ненулевой `OutboxCursor` принимается и игнорируется; новые отправители кодируют ноль.


# ERRATA v2.4.7

## E-21. §13.1 — каноническая структура и resource bounds для STATE_DIGEST

**Дефект:** декодер STATE_DIGEST приводил объявленное количество bucket rows из varint к `int` без предварительного ограничения, принимал произвольную длину prefix и не требовал уникального/упорядоченного набора bucket rows или EOF после последней строки. Некорректные строки могли вызвать чрезмерную аллокацию, неоднозначное представление одного digest и расхождение поведения реализаций.

**Нормативно:**
1. `RadixBits` обязан быть кратен 8 и находиться в диапазоне 8..256. Длина каждого bucket prefix строго равна `RadixBits / 8`.
2. `bucketCount` не превышает 100 000 и до итерации дополнительно проверяется на возможность размещения всех минимальных строк в оставшемся payload. Каждая строка содержит `prefixLen u8 | prefix | count u32 | xor16 | sum16 | rollup32`.
3. Bucket rows передаются в строго возрастающем лексикографическом порядке по байтам prefix. Дубликаты и неупорядоченные строки отвергаются.
4. `count` каждой передаваемой bucket row должен быть положительным; пустые bucket rows не кодируются.
5. После последней bucket row reader обязан находиться в EOF; trailing bytes запрещены.
6. Перед вычислением divergent prefixes обе структуры проверяются на корректные длины root/accumulators, допустимый radix, положительные counts и строго упорядоченные уникальные prefixes. Namespace и RadixBits двух сообщений обязаны совпадать.
7. Локальный builder принимает только byte-aligned RadixBits 8..256 и namespace в диапазоне u16.

**Wire layout:** не меняется для корректных сообщений. Ограничения фиксируют единственную каноническую форму STATE_DIGEST и ограничивают работу декодера по недоверенному payload.


# ERRATA v2.4.8

## E-22. §13.1–13.2 — resource bounds и полная проверка NEED_RANGE / NEED_KEYS

**Дефект:** NEED_RANGE принимал prefix произвольной длины и игнорировал trailing bytes. NEED_KEYS приводил varint count к `int` без проверки диапазона, не проверял соответствие количества оставшемуся payload, допускал повторные record IDs и также игнорировал trailing bytes.

**Нормативно:**
1. NEED_RANGE prefix имеет длину от 0 до 32 байт включительно. Пустой prefix сохраняет значение terminator в AutoReconcile. Более длинные prefix отвергаются до чтения/использования.
2. NEED_RANGE decoder обязан потребить payload полностью; trailing bytes запрещены.
3. NEED_KEYS содержит не более 100 000 record IDs. Count проверяется как `ulong` до итерации и обязан быть не больше `remainingPayloadBytes / 16`.
4. Каждый NEED_KEYS record ID — ровно 16 байт; повторяющиеся IDs отвергаются. Encoder также отвергает повторные ID после canonical B128 normalization.
5. NEED_KEYS decoder обязан потребить payload полностью; trailing bytes запрещены.
6. Encoder NEED_RANGE/NEED_KEYS обязан проверять диапазон namespace u16 и установленные ограничения до сериализации.

**Wire layout:** без изменений для корректных сообщений.


# ERRATA v2.4.17

## E-23. §8.4–8.8 / §18.4 — канонические CRDT payloads и SCHEMA_MAP

**Дефект:** CRDT-декодеры могли принимать повторные компоненты/dots, неупорядоченные записи и trailing bytes; oversized counts приводились к `int` до проверки оставшегося payload. Конфликтующие значения с одинаковой идентичностью SEQ_FRACTIONAL или BLOB_REF могли разрешаться выбором локального operand. SCHEMA_MAP терял дубли field IDs при помещении в HashSet и мог молча пропускать malformed descriptors во время Learn.

Реализация обязана проверять counts до narrowing/allocation, строгий порядок и уникальность, полное потребление payload и конфликт идентичности до merge/publication. Для SCHEMA_MAP дубли descriptor keys и field IDs, неупорядоченные field IDs и пересечение active/retired IDs являются ошибкой всего payload.

**Wire format:** байты, создаваемые корректными прежними encoder-ами, не меняются. Изменяется только приемная строгость: неканонические/неоднозначные payloads отклоняются.

# ERRATA v2.4.18

## E-24. §8.3 / §10.1 / §13.4 / §17.23 — глобальная идентичность ChangeId и защита от equivocation

**Дефект:** дедупликация по (senderPeer, namespaceId, ChangeId) рассматривает одно логическое изменение, доставленное через независимые маршруты, как разные операции. После удаления/компактизации исходной Outbox-записи проверка только текущей очереди также перестаёт быть достаточной. Это позволяет повторно применить и ретранслировать кольцевое эхо. Обратная проблема — повторное использование одного ChangeId для другого содержимого — делает provenance неоднозначным.

**Нормативно:**

1. В пределах одной локальной реплики логическая идентичность операции определяется парой (namespaceId, ChangeId). NodeId локальной реплики задаётся самим durable state image и не повторяется в каждом ключе. Immediate sender, маршрут, session alias, issuer BatchId и relay-local sequence не входят в identity. Одинаковый ChangeId в разных namespace — разные identities.
2. При первом принятии узел вычисляет semantic fingerprint операции после разрешения исходного AuthorNodeId. Fingerprint обязан быть независим от транспортного alias и включать namespace, envelope RecordId, opKind и все семантически значимые поля операции: тип операции, field ID (если применимо), KeyEpoch, HLC wall/logical, исходного AuthorNodeId и точные value bytes для FieldWrite; для FieldTomb и RecordTombstone — их tombstone/lifecycle semantics и соответствующие идентификаторы. Если для операции применим causal trailer, fingerprint включает множество ChangeId-зависимостей в canonical sorted-unique форме; отсутствие trailer и пустое множество эквивалентны.
3. **Same identity + same fingerprint:** операция уже известна этой реплике независимо от sender/маршрута. Она не применяется повторно и не добавляется в relay Outbox повторно. При этом новый корректный входящий batch от другого peer всё равно проходит обычную проверку cursor/digest и фиксирует собственный batch receipt/receive cursor; peer получает обычный ACK после durable commit.
4. **Same identity + different fingerprint:** это ChangeId equivocation/protocol conflict. Весь входящий batch отклоняется до WAL append и публикации field state, cursor, receipt, dedup ledger или relay entries. Частичный commit запрещён.
5. Право на relay определяется первым принятием identity этой репликой, а не результатом LWW merge. Впервые увиденная операция, проигравшая текущему LWW winner, остаётся relay-eligible согласно E-8. Повторно увиденная identity не становится relay-eligible даже при доставке от другого peer.
6. Локально созданная операция регистрирует (namespaceId, ChangeId, fingerprint) атомарно с локальным field state, Outbox и WAL до того, как операция может быть опубликована транспортом. Возврат собственной операции через mesh подавляется глобальным ledger даже после компактизации локального Outbox.
7. Legacy identity, для которой мигрированное состояние не содержит fingerprint, является **unknown-but-seen**: её консервативно считают дубликатом и не применяют/не ретранслируют. При первом повторном получении узел может закрепить вычисленный fingerprint в том же durable commit, что и batch receipt/cursor, но не пере-применяет операцию. Это не даёт задним числом доказать отсутствие equivocation для исторической операции.
8. Dedup ledger не удаляется по TTL, локальному Outbox ACK или relay payload ACK. GC допустим только после отдельного protocol-safe dedup horizon, который гарантирует невозможность легального повторного предъявления старого ChangeId. Пока такой horizon не определён, identity удерживается; настроенный resource cap при заполнении должен отклонить новый batch атомарно, а не вытеснять старые identities.

**Fingerprint implementation:** текущая реализация использует BLAKE3-128 от canonical semantic representation; all-zero digest зарезервирован для unknown legacy marker. Fingerprint — локальный derived index, он не передаётся в DELTA_BATCH и не меняет RecordsRoot/BatchDigest. Реализации могут использовать иной collision-resistant fingerprint, если сохраняют перечисленную семантическую эквивалентность и fail-closed equivocation behavior.

**Совместимость:** DELTA_BATCH, snapshot и ACK wire layouts не меняются. E-24 уточняет и усиливает E-8/E-13: route-scoped SeenChanges больше не является источником глобальной dedup истины; дополнительная E-13 проверка байт-идентичного собственного состояния остаётся допустимым локальным echo guard. NodePersistence v12 — локальный формат хранения, не wire revision.

# ERRATA v2.4.19

## E-25. §11.5 / §11.8 / §12.20 — fail-closed tombstone retention

**Дефект:** прежняя формулировка `TOMBSTONE_MIN_TTL=7 days` и scalar `TombstoneCutoffWall` могла трактоваться как достаточное основание удалить tombstone. Текущий GC_NOTICE не содержит подтверждённого per-author stable frontier, не фиксирует durable namespace cutoff и не доказывает, что все активные peers применили baseline. WatermarkGate также не подключён ко всем incremental/snapshot acceptance paths. Удаление по возрасту могло привести к resurrection отставшей операции.

**Нормативно:** §11.5 заменён fail-closed retention contract. TTL — только минимальный возраст-кандидат, не safe watermark. Tombstone/ghost reclamation запрещён до durable per-author frontier, подтверждённого всеми peers текущего baseline, fencing stale/quarantined peers и обязательного full resync для них и новых peers. Snapshot/feed watermark обязаны иметь одну atomic barrier. GC_NOTICE cutoff остаётся advisory и сам по себе не разрешает удаление. До полной реализации gate все tombstones сохраняются.

**Текущая реализация:** `GcNotice.PurgeBelowCutoff` возвращает 0 и не удаляет live fields, field tombstones или record lifecycle tombstones. Это намеренный fail-closed behavior, а не завершённый GC.

**Wire format:** без изменений. E-25 ужесточает интерпретацию существующего GC_NOTICE и запрещает небезопасное поведение; будущий durable frontier может потребовать отдельной protocol revision после определения полного handshake/ACK contract.


# ERRATA v2.4.22

## E-26. §§10.7 / 11.2–11.9 — independent durable retention horizons

**Дефект:** один общий peer ACK, snapshot baseline или membership hint нельзя использовать для удаления всех видов метаданных. Inbox receipt, ChangeId fingerprint, provider apply-token receipt, receive cursor/digest-chain checkpoint, outbound/relay payload и tombstone имеют разные причины удержания. Удаление receipt/identity по TTL или удаление ChangeId по peer ACK допускает повторную доставку, equivocation или resurrection.

**Нормативно:**

1. Outbound/relay payload compaction использует только contiguous per-author peer ACK/baseline frontier и отдельный local consumer ACK, если он существует. Этот delivery frontier не разрешает удалять Inbox receipts, ChangeId fingerprints, CompletedPendingApply tokens или tombstones.
2. Inbox receipt identity остаётся `(senderNodeId, senderEpoch, namespaceId, batchId)`. Authenticated transport peer epoch хранится отдельно и не подменяет author/issuer epoch.
3. Storage-backed receipt GC разрешён только когда более новая transport-peer incarnation durably registered и её complete initial-sync baseline durably committed, old epoch durably fenced by monotonic retired-through marker, и receipt deletion commits atomically with that fence. Retirement MUST be blocked while a matching or epoch-unknown PendingApply is unresolved. Receive entry points MUST reject retired/epoch-less traffic after a retirement fence. Legacy receipts with unknown transport epoch MUST be retained until an exact authenticated duplicate from a registered current epoch re-attributes them. Active-epoch receipts and CompletedPendingApply tokens are not deleted by this rule.
4. The existing MEMBERSHIP message and InterestedPeers roster are not an authoritative namespace membership set. They MUST NOT be used as the denominator for ChangeId or tombstone GC.
5. ChangeId ledger GC remains disabled until each operation carries immutable origin author, author epoch and origin sequence unchanged through every relay; a committed authoritative namespace roster generation exists; and every member in that roster has durably published a signed monotonic retention checkpoint with a contiguous applied frontier for each origin stream. Missing members/checkpoints contribute zero. Provenance-less legacy ledger rows are non-collectable. No TTL, HLC-age, LRU, size-based eviction, Outbox ACK or relay ACK may remove ChangeId identity.
6. Tombstone/ghost GC remains disabled until the same authoritative roster/frontier proof exists and every member has installed the same authoritative full-snapshot generation/digest. A merge snapshot does not delete rows absent from the snapshot. Rejoining or removed members MUST install an atomic FULL_REPLACE snapshot before incremental deltas are accepted.
7. A retention checkpoint and any resulting physical deletion must be crash-consistent. GC must fail closed on roster mismatch, epoch regression, missing author frontier, incomplete PendingApply, immutable outbound reservation, or snapshot/feed barrier mismatch.

**Текущая реализация:** retired-transport-epoch Inbox receipt GC is implemented conservatively in StorageMetadataStore. ChangeId ledger GC and tombstone/ghost GC remain disabled. GcNotice.PurgeBelowCutoff returns zero. No wire payload layout changes are introduced by E-26; new origin-coordinate, roster-certificate and retention-checkpoint messages require a separately specified negotiated protocol revision before implementation.

## 10.7. Receipt identity and resolved author

The durable Inbox idempotency key is exactly `(senderNodeId, senderEpoch, namespaceId, batchId)`. The resolved `authorNodeId` is a separate receive-stream coordinate and MUST NOT be appended to the receipt key: otherwise the same BatchId could create multiple receipts by changing the resolved author. The receipt commitment validates the batch header; per-author receive progress is updated only on first acceptance.

## 11.9. Per-author retention and receipt separation

Outbox/relay payload compaction, Inbox receipt retention, ChangeId dedup retention and tombstone reclamation are independent horizons. A peer ACK may authorize a contiguous payload prefix only. It MUST NOT delete Inbox receipts, ChangeId fingerprints, provider idempotency tokens or tombstones. In the absence of a durable protocol-defined checkpoint for one of those domains, retain the corresponding metadata (fail closed).

## 13.7. Relay alias failure atomicity

If any retained relay operation's original author has no alias in the target session, the sender MUST fail the complete batch with `UNKNOWN_ALIAS`; it MUST NOT silently skip the operation. Skipping would create an author-stream sequence hole and make later cursor continuity impossible.
